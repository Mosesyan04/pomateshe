# Pomateshe — API-подход

Статус: проектный контракт-уровня документ. Конкретные route handlers не реализуются в этой задаче.

## 1. Общий подход

- API живёт внутри Next.js: `app/api/**/route.ts` для REST-подобных эндпоинтов, вызываемых
  извне (интеграции, webhook от Google Calendar) или клиентом там, где нужен явный HTTP-контракт
  (например, выдача presigned URL, выдача токена комнаты доски).
- Внутренние мутации кабинета (создание урока, отметка оплаты и т.п.) по умолчанию — Next.js
  **Server Actions**, а не отдельные REST-эндпоинты: меньше boilerplate, автоматическая защита
  от произвольных cross-origin вызовов. REST используется там, где нужен стабильный внешний
  контракт (webhooks, будущие мобильные клиенты, будущие интеграции).
- Версионирование явным префиксом (`/api/v1/...`) не вводится в MVP — при одном разработчике
  и отсутствии внешних потребителей API это преждевременная сложность (Правило 10 ТЗ).
  Совместимость обеспечивается аддитивными изменениями (новые опциональные поля, не удаление
  существующих) до появления реальной необходимости в версионировании.

## 2. Аутентификация запросов

- Браузерные запросы — сессионная cookie (см. `docs/AUTH.md`), CSRF-защита по правилам
  `docs/SECURITY.md` §5.
- Webhook от внешних сервисов (Google Calendar push-уведомления) — проверка подписи/токена
  канала, не сессия пользователя.
- Внутренние cron-вызовы (retention доски, напоминания об оплате) — защищённый секретный
  заголовок (`X-Internal-Secret`), сравнение constant-time, эндпоинт недоступен без него даже
  авторизованному пользователю платформы.

## 3. Формат ответа

```jsonc
// успех
{ "data": { /* ресурс или массив */ }, "meta": { /* пагинация, если применимо */ } }

// ошибка
{ "error": { "code": "FORBIDDEN", "message": "человекочитаемое сообщение (без утечки внутренних деталей)" } }
```

- Коды ошибок — стабильный enum (`UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`,
  `RATE_LIMITED`, `CONFLICT`, `INTERNAL_ERROR`), не строковый текст исключения — текст исключения
  никогда не возвращается клиенту напрямую (риск утечки деталей реализации/стека).
- Валидация входных данных — zod-схемы на границе API, отдельно от Prisma-схемы (не путать
  DB-схему и API-контракт — они могут расходиться, например API принимает `price` в рублях,
  а БД хранит `priceCents`).

## 4. Пагинация

- Cursor-based (по `id`/`createdAt`), не offset-based — устойчивее к вставке новых записей
  между запросами страниц (актуально для списка уроков, который растёт каждый день).

## 5. Примеры контрактов ключевых ресурсов (иллюстративно, не исчерпывающе)

| Метод/путь | Назначение | Кто может вызывать |
|---|---|---|
| `GET /api/public/teachers/:slug` | Публичные данные страницы преподавателя | Без авторизации |
| `POST /api/uploads/presign` | Выдача presigned URL на загрузку файла | teacher, student (владелец контекста) |
| `POST /api/whiteboard/:lessonId/token` | Выдача короткоживущего токена подключения к доске | Участник конкретного урока |
| `GET /api/lessons?from=&to=` | Список занятий преподавателя за период | teacher (свои), student (свои) |
| `POST /api/integrations/google-calendar/oauth/callback` | Callback OAuth Google Calendar | Google (проверка `state`) |
| `POST /api/webhooks/google-calendar` | Push-уведомление об изменении календаря | Google (проверка канала) |
| `POST /api/internal/cron/whiteboard-retention` | Плановая очистка старых досок | Внутренний cron (секретный заголовок) |

## 6. Rate limiting и таймауты

См. `docs/SECURITY.md` §4. API-таймаут по умолчанию — короткий (несколько секунд) для обычных
CRUD-операций; операции с внешними интеграциями (Google Calendar sync) выполняются асинхронно
там, где могут превысить разумный таймаут запроса, а не блокируют HTTP-ответ пользователю.

## 7. Наблюдаемость

- Каждый ответ с ошибкой 5xx логируется с `requestId` для трассировки — `requestId`
  возвращается клиенту в заголовке ответа для возможности сослаться на конкретный инцидент
  в поддержке.
