### 1a. Открытый вопрос — лимит одновременных подключений ("6 обработчиков запросов")

Поддержка SprintHost сообщила лимит **«6 обработчиков запросов на одном веб-сервере»**, но
сама формулировка неоднозначна и требует уточнения (уточняется у поддержки, ответ ожидается):

- Если это лимит на **число одновременных коротких HTTP-запросов в очереди** (типично для
  Node-хостинга через Passenger-подобный процесс-менеджер) — это, скорее всего, не блокирует
  архитектуру: обычные API-запросы платформы короткие, такой лимит некритичен для Next.js-части.
- Если это лимит на **число одновременных долгоживущих соединений вообще, включая WebSocket**
  (т.е. каждое открытое WS-соединение для доски постоянно занимает один из 6 "обработчиков"
  на всё время урока) — это **жёстко ограничивает realtime-доску 6 одновременными участниками
  на весь сервер**, а не на один урок, что для многотенантной платформы неприемлемо уже на
  старте (даже 2-3 параллельных урока с 2+ участниками каждый могут упереться в лимит).

**Пока ответ не получен, этот пункт считается блокирующим только для решения о размещении
realtime-сервиса** (не всего приложения) — остальной чек-лист (Node, WebSocket "в принципе
поддерживается", Postgres, cron, РФ-регион) подтверждён независимо от этого лимита. См. §2 —
план действует в двух ветках в зависимости от ответа.

Пункты "поддержка Node" и "поддержка WebSocket" сами по себе больше не блокируют выбор
хостинга — оба подтверждены. Сценарий B (§2) остаётся в документе только как fallback на
случай, если ответ по лимиту подключений (§1a) окажется неприемлемым для WebSocket.

## 1.1 Fallback-матрица **[review-2: новый раздел]** — что делать, если конкретный компонент недоступен

Ничего из характеристик SprintHost не выдумывается — таблица ниже описывает **реакцию
архитектуры**, если ответ на конкретный пункт чек-листа §1 окажется "нет". По состоянию на
последний ответ поддержки первая строка (Docker) — уже не гипотеза, а рабочее предположение
для планирования (Docker не упоминался в ответе, явно не подтверждён).

| Недоступно на SprintHost | Fallback | Что НЕ делаем |
|---|---|---|
| Docker/Docker Compose — **[статус: вероятно применяется, ожидает прямого подтверждения]** | Нативный деплой: `systemd`-unit для Next.js custom server + `systemd`-unit для realtime-процесса, менеджер процессов (PM2 как альтернатива systemd) вместо контейнеров; Postgres — нативная установка через пакетный менеджер ОС хоста (Postgres на SprintHost подтверждён отдельно — см. §1, вопрос только в способе управления процессами приложения, не в СУБД) | Не переписываем приложение под требования хостинга — меняется только способ запуска процесса, не архитектура |
| Постоянный Node.js-процесс (только CGI/FastCGI-вызов на запрос) | Next.js и realtime-сервис переносятся на отдельный VPS/PaaS с поддержкой Node; SprintHost используется только для DNS (и, опционально, для статических юридических страниц как fallback-заглушки) | Не пытаемся адаптировать Next.js под CGI-модель — это архитектурно несовместимо с SSR+Server Actions+WebSocket |
| WebSocket (Node есть, но прокси/файрвол хостинга режет upgrade) | Realtime-сервис (только он, не всё приложение) выносится на отдельный VPS с прямым доступом, минуя ограничивающий прокси; либо, как временная деградация — long-polling транспорт для Yjs (y-websocket поддерживает HTTP-fallback ценой задержки синхронизации) — рассматривается только как временная мера, не постоянное решение | Не отказываемся от realtime-доски как функции — ищем альтернативный транспортный путь именно для неё |
| Managed/доступный PostgreSQL | Managed Postgres у РФ-провайдера (Selectel, VK Cloud, Yandex Cloud) отдельно от хостинга приложения; приложение подключается по сети к внешней БД | **Не переходим на MySQL/другую СУБД, даже если она "есть из коробки"** на shared-хостинге — весь дизайн RLS-изоляции (`docs/MULTI_TENANCY.md`) требует PostgreSQL Row-Level Security, у MySQL нет прямого эквивалента; смена СУБД — это пересмотр центрального архитектурного решения о multi-tenancy, не рядовая замена компонента |
| Возможность держать секреты вне репозитория (нет панели управления переменными окружения) | `.env`-файл на сервере с ограниченными правами доступа (`chmod 600`, вне webroot) как минимально достаточная альтернатива secret-менеджеру хостинга | Не коммитим секреты в репозиторий ни при каком варианте хостинга — это не подлежит компромиссу (`docs/SECURITY.md` §7) |

Общий принцип: чем меньше SprintHost может дать из списка §1, тем больше компонентов
переезжает на отдельный VPS/PaaS, вплоть до полного Сценария B (домен и максимум статика
остаются на SprintHost, всё остальное — в другом месте). Ни один из fallback-вариантов не
меняет модель данных, RLS-стратегию или выбор PostgreSQL — эти решения не зависят от хостинга.

## 1.2 Что зафиксировано независимо от хостинга **[review-2: новый раздел]**

Явно отделяем то, что решено архитектурой и не изменится в зависимости от ответа SprintHost,
от того, что решение по SprintHost определяет:

**Зафиксировано (не зависит от хостинга):**
- Технологический стек — Next.js/TypeScript/PostgreSQL/Prisma/Yjs (`docs/ARCHITECTURE.md` §3).
- PostgreSQL как СУБД (не меняется на MySQL/другое ни при каком варианте, см. §1.1).
- Требование физического расположения БД и объектного хранилища в РФ (152-ФЗ) — сужает выбор
  провайдера, но не зависит от того, где именно крутится сам Next.js-процесс.
- Схема данных, RLS-стратегия, модель ролей (`docs/MULTI_TENANCY.md`, `docs/DATABASE.md`).
- Домен `pomateshe.ru` остаётся точкой входа в любом сценарии — меняется только то, куда
  указывает DNS.

**Подтверждено ответом SprintHost (переехало из "зависит" в "зафиксировано"):**
- Node.js-процесс приложения размещается на SprintHost (постоянный процесс поддерживается).
- Способ деплоя — нативный `systemd`/PM2, не Docker Compose (Docker, вероятно, недоступен, §1.1).
- Управление cron — доступно на SprintHost, отдельный VPS ради этого не нужен.
- PostgreSQL и расположение серверов в РФ — подтверждены, требование 152-ФЗ по локации
  выполнимо в рамках одного SprintHost-тарифа, без обязательного переноса БД к другому провайдеру.

**Всё ещё зависит от ответа SprintHost:**
- Размещение realtime-сервиса (доска) — на SprintHost вместе с основным приложением или на
  отдельном VPS — решается ответом по лимиту "6 обработчиков запросов" (§1a).
- Лимиты диска/RAM/CPU и стоимость апгрейда — не выяснялось.
- Процедура получения TLS-сертификата — не выяснялось.
- Разрешены ли исходящие HTTPS-запросы (нужны для Google Calendar API, S3-совместимого
  хранилища) — не выяснялось.

## 2. Два сценария деплоя (см. `docs/ARCHITECTURE.md` §8)

По состоянию на подтверждённые пункты чек-листа (§1) базовые условия Сценария A выполнены
(Node.js, WebSocket, PostgreSQL, cron, РФ-регион — все подтверждены). Открытыми остаются два
момента: способ деплоя без Docker (§1.1, решаемо — нативный процесс-менеджер) и лимит
одновременных подключений (§1a, решается уточнением у поддержки). Ниже — уточнённые сценарии
с учётом этого.

### Сценарий A — подтверждён для Next.js-части, адаптирован под отсутствие Docker

```
[Caddy/nginx: TLS, pomateshe.ru] → [Next.js custom server + WS upgrade] → [PostgreSQL]
                                                                        → [S3-совместимое хранилище]
```
Деплой — не `docker compose up -d` (Docker, вероятно, недоступен, см. §1.1), а нативный запуск
процесса через `systemd`/PM2 на том же сервере SprintHost. Postgres — либо нативная установка
там же, либо managed-инстанс у РФ-провайдера, если конкретный тариф SprintHost не даёт удобного
управления PostgreSQL (это уже не блокирующий, а конфигурационный вопрос — сама СУБД подтверждена).

**Realtime-сервис (доска) — под вопросом до ответа по §1a**:
- Если лимит "6 обработчиков" не относится к долгоживущим WebSocket-соединениям — realtime-сервис
  разворачивается на том же сервере, что и основной Next.js-процесс, оба под Сценарием A.
- Если лимит относится и к WebSocket, и 6 одновременных подключений на сервер недостаточно —
  применяется соответствующая строка fallback-матрицы (§1.1, "WebSocket ... режет upgrade/лимит
  подключений"): realtime-сервис выносится на отдельный VPS, а Next.js-часть остаётся на
  SprintHost. Это частичный Сценарий B — не для всего приложения, а только для одного компонента.

### Сценарий B — SprintHost не подходит вообще (маловероятно по текущим ответам, сохранён как fallback)

```
DNS: pomateshe.ru → VPS/PaaS (Node-совместимый, РФ-регион по 152-ФЗ)
[Caddy/nginx] → [Next.js custom server + WS] → [Managed/self-hosted PostgreSQL]
                                              → [S3-совместимое хранилище]
```
Домен остаётся тем же, меняется только точка, куда указывает DNS. Архитектура приложения
идентична Сценарию A — решение о хостинге не меняет код. По текущим ответам этот сценарий
целиком уже не основной рабочий вариант (Node/WebSocket/Postgres на SprintHost подтверждены),
но остаётся планом на случай, если ответ по §1a окажется настолько ограничивающим, что
разумнее перенести не только realtime, а всё приложение.

## 3. Окружения

| Окружение | Назначение | БД |
|---|---|---|
| local | Разработка на машине разработчика | Postgres в Docker, локальные данные |
| staging | Проверка перед релизом, прогон E2E | Отдельная БД, синтетические данные |
| production | Боевая среда | Managed/self-hosted Postgres с бэкапами |

Для проекта с одним разработчиком staging может быть временным (поднимается перед крупным
релизом), не обязательно постоянно работающим окружением — экономия ресурсов допустима
(Правило 10 ТЗ), но перед первым продакшен-релизом staging обязателен хотя бы один раз для
прогона миграций и E2E на данных, близких к боевым.

`DATABASE_URL` (рантайм-роль `pomateshe_app`, **[review-2]** отдельно от `DATABASE_URL`

## 5. Миграции

- `prisma migrate deploy` выполняется как явный шаг деплоя (не `migrate dev`, не автоматический
  `db push` в проде), **[review-2]** и обязательно под ролью `pomateshe_migrator`, отдельной от
  рантайм-роли `pomateshe_app` — использование одной и той же роли для миграций и рантайма
  делает `pomateshe_app` владельцем таблиц и тихо отключает RLS (см. `docs/MULTI_TENANCY.md`
  §2.3 — это главная находка второго review, обязательна к соблюдению с первой миграции).
- Миграции — часть PR, ревьюятся так же, как код. Каждая новая tenant-таблица обязана в одной
  миграции: `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`, `CREATE POLICY`,
  `GRANT ... TO pomateshe_app` (все четыре пункта — `docs/MULTI_TENANCY.md` §2.3).
- Откат — через новую компенсирующую миграцию, не через ручное редактирование БД в проде.

## 6. Процесс релиза (минимально достаточный для одного разработчика)

**[обновлено с учётом ответа SprintHost]** Docker остаётся стандартом для локальной разработки
(`docker compose up` для Postgres и т.п., см. §3) и, если Docker на проде всё же подтвердится
позже — для production тоже. Пока Docker на SprintHost не подтверждён, production-релиз
описан через нативный деплой (пп. 2-3 ниже), не через `docker compose`.

1. PR → CI (lint, typecheck, unit, integration тесты, включая тесты изоляции тенантов).
2. Мердж в основную ветку → сборка Next.js/realtime под production (`next build` и т.п.) →
   миграции на staging (`prisma migrate deploy` под ролью `pomateshe_migrator`, §5) → E2E на staging.
3. Ручное подтверждение → деплой на production: выкладка собранных артефактов на SprintHost по
   SSH (подтверждён) → перезапуск `systemd`/PM2-юнитов (§1.1) → миграции на production.
4. Health-check после деплоя (доступность `/api/health`, соединение с БД) — при ошибке
   автоматический откат на предыдущий образ, если хостинг это поддерживает, иначе — ручной откат
   по runbook (создаётся на этапе реализации).
