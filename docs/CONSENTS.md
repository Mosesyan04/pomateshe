# Pomateshe — Согласия, cookie, юридические страницы

Статус: проектные требования. **Юридические тексты (оферта, политика конфиденциальности) не
копируются с сайтов конкурентов (правило ТЗ №5, например TutorOnline) — пишутся/заказываются
отдельно, этот документ описывает только структуру данных и технические требования, не сам текст.**

## 1. Правовой контекст

Домен `.ru` и русскоязычная аудитория → применяется 152-ФЗ «О персональных данных». Ключевые
технические следствия:

- Персональные данные (имя, email, телефон, переписка/заметки об ученике) должны первично
  собираться и храниться на серверах в РФ (влияет на выбор БД/хостинга/объектного хранилища,
  см. `docs/ARCHITECTURE.md` §8, `docs/FILE_STORAGE.md` §2).
- Нужно явное согласие на обработку персональных данных, отдельное от согласия с офертой.
- Пользователь должен иметь возможность запросить удаление своих данных (§4 ниже).
- Оператор персональных данных (владелец платформы) должен быть готов к уведомлению
  Роскомнадзора при определённых условиях — это организационное, не архитектурное требование,
  но фиксируется здесь как контекст, влияющий на необходимость вести `ConsentRecord`.

## 2. Типы согласий (`ConsentRecord.type`, см. `docs/DATABASE.md` §2)

| Тип | Когда запрашивается | Обязательность |
|---|---|---|
| `pdn_processing` | При регистрации (преподаватель и ученик) | Обязательно, блокирует регистрацию без согласия |
| `privacy_policy` | При регистрации | Обязательно |
| `offer` | При регистрации преподавателя (публичная оферта об использовании платформы) | Обязательно для teacher |
| `cookie_analytics` | При первом визите (cookie-баннер) | Опционально, не блокирует использование сайта |
| `cookie_marketing` | При первом визите | Опционально |

- Каждая запись хранит `policyVersion` — при изменении текста политики версия увеличивается,
  и согласие запрашивается заново при следующем входе, если версия устарела (нельзя молча
  считать старое согласие действующим для нового текста).
- `ip` и `userAgent` фиксируются на момент согласия — доказательная база на случай спора.

## 3. Cookie consent

- Баннер блокирует **не необходимые** cookie (аналитика, маркетинг) до явного согласия —
  сессионная cookie аутентификации не требует согласия (строго необходима для работы сервиса,
  что является законным основанием без запроса согласия).
- Технически: аналитические скрипты не загружаются до получения `cookie_analytics` согласия
  (не просто "cookie не читается", а сам скрипт не инициализируется) — иначе баннер декоративен.
- Выбор пользователя запоминается (`ConsentRecord` для авторизованных, локальное хранилище +
  best-effort для анонимных посетителей публичных страниц) и может быть изменён в любой момент
  через настройки/футер.

## 4. Право на удаление данных

**[review-2]** С переходом на модель "один ученик — несколько преподавателей"
(`docs/MULTI_TENANCY.md` §1.1) это стало двумя разными операциями, которые нельзя путать:

1. **Отвязка от одного преподавателя** — удаление конкретной `TeacherStudentLink` (и всех
   данных, привязанных к ней: `Lesson`, `Homework`, `MaterialFile` этого преподавателя) без
   затрагивания связей ученика с другими преподавателями и без удаления самого `User`.
2. **Полное удаление аккаунта** — запрос на удаление `User` целиком каскадно затрагивает
   **все** его `TeacherStudentLink` у всех преподавателей платформы, а не только у одного —
   продуктовый интерфейс должен явно предупреждать об этом различии перед подтверждением,
   чтобы ученик (или преподаватель, инициирующий отвязку) не перепутал "отвязать у себя" с
   "удалить аккаунт ученика полностью".

Процедура полного удаления: запрос → подтверждение → каскадное удаление персональных данных:
`User`, все связанные `TeacherStudentLink` (и через них — `Lesson`, `Homework`), файлы из
объектного хранилища, активные доски.
- Что **не удаляется** немедленно: финансовые записи (`Lesson.priceCents`/`paidAt`), если по
  закону/бухгалтерским требованиям нужен срок хранения — обезличиваются (отвязываются от
  персональных идентификаторов), а не физически стираются, если это создаёт юридический риск
  для преподавателя-ИП/самозанятого. Точный срок — уточняется на этапе реализации с учётом
  налогового законодательства (вне компетенции этой архитектуры).
- Бэкапы: запись об удалении применяется к бэкапам по мере их ротации (см. `docs/DATABASE.md`
  §6) — немедленное удаление из уже созданных бэкапов не гарантируется технически, это
  фиксируется в самой политике конфиденциальности, чтобы не давать ложных обещаний пользователю.
- **[review-2]** `ConsentRecord` и `AuditLog` не удаляются вместе с аккаунтом — они
  обезличиваются (ссылка на `userId` перестаёт указывать на восстановимые персональные данные,
  но сама запись "когда и какая версия политики была принята" сохраняется) — это доказательная
  база, нужная в т.ч. и после удаления аккаунта, тот же принцип, что и у финансовых записей
  выше (см. сводную таблицу retention — `docs/DATABASE.md` §7).

## 5. Юридические страницы (структура, не текст)

- `/legal/offer` — публичная оферта на использование платформы.
- `/legal/privacy` — политика конфиденциальности (обработка ПДн).
- `/legal/cookies` — политика использования cookie.
- Все три — статические страницы (SSG), версионируются вместе с `policyVersion` в §2.
- Ссылки на эти страницы обязательны в футере и в формах регистрации/согласия.

## 6. Ответственность реализации

Тексты этих страниц — не инженерная задача, требуют юридической проверки перед публикацией
(особенно для 152-ФЗ и налогового статуса преподавателей-ИП/самозанятых). Архитектура готова
принять эти тексты как контент, версионировать их и связывать с `ConsentRecord`.
