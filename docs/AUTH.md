# Pomateshe — Аутентификация и сессии

Статус: пересмотрено во втором архитектурном review. **Auth.js больше не является выбором по
умолчанию** — см. §0 обоснование пересмотра. Модель ниже — минимальная кастомная сессионная
аутентификация.

## 0. Пересмотр: нужен ли Auth.js

Первая версия документа выбирала Auth.js (NextAuth v5) "оптом" — за DB-сессии, Credentials и
Google OAuth "из коробки". При повторном рассмотрении это решение было избыточным:

- **Google OAuth как способ входа не был требованием ТЗ** — ТЗ просит "регистрацию и
  авторизацию" с ролями admin/teacher/student, не социальный вход. Единственная реальная
  причина, по которой в системе вообще нужен Google OAuth — привязка Google Calendar
  (`docs/CALENDAR.md`), и это **не аутентификация пользователя платформы**, а отдельная
  интеграция от имени уже вошедшего преподавателя. Добавление OAuth-как-логина без этого
  требования увеличивает поверхность атаки без функциональной необходимости (открытый
  redirect, account-linking edge cases — что если email в Google-аккаунте совпадает с уже
  зарегистрированным через пароль пользователем — это отдельный класс уязвимостей account
  takeover, требующий explicit handling) — нарушает прямое указание "не добавляй OAuth без
  обоснованной необходимости".
- **Credentials provider в Auth.js — намеренно "сделай сам"**: сама библиотека не хеширует и
  не проверяет пароли за разработчика в Credentials-режиме — эта логика пишется руками в любом
  случае. То есть именно та часть, ради которой Auth.js обычно берут "чтобы не писать auth с
  нуля", в Credentials-сценарии всё равно пишется руками.
- **DB-сессии** (главный оставшийся довод в пользу Auth.js) реализуются напрямую через одну
  таблицу `Session` и штатные механизмы Next.js (cookies), без необходимости в адаптере.
- Auth.js v5 на момент написания первой версии документа долго оставался в статусе beta —
  для проекта одного разработчика дополнительный риск смены API версии — ещё один аргумент
  против внешней зависимости там, где вся нужная функциональность умещается в ~150-200 строк
  собственного, полностью понятного кода.

**Решение**: MVP использует минимальную кастомную модель (§1-6). Auth.js не устанавливается.
Если в будущем появится реальная необходимость в множестве провайдеров входа — решение
пересматривается отдельно, с тем же анализом необходимости, а не "добавляем библиотеку про запас".

## 1. Способ входа

**Только email + пароль.** Google используется исключительно для привязки Calendar
(`docs/CALENDAR.md` §2) — это отдельный OAuth-flow, инициируемый из настроек кабинета
преподавателя, не связанный с логином и не создающий `User`/сессию платформы. Токены календаря
хранятся в `CalendarIntegration`, полностью отдельно от механизма входа.

## 2. Хранение пароля и сессии

- Пароль — Argon2id (`@node-rs/argon2` или эквивалент), параметры — по актуальным
  рекомендациям OWASP на момент реализации.
- Сессия: при успешном входе генерируется случайный токен (`crypto.randomBytes(32)`,
  base64url) → в БД сохраняется **только его SHA-256 хэш** (`Session.tokenHash`, см.
  `docs/DATABASE.md` §2) → сырой токен уходит клиенту в `httpOnly`, `secure`,
  `sameSite=lax` cookie. Хранение хэша, а не сырого токена, означает, что утечка БД (бэкап,
  дамп, SQL-инъекция) сама по себе не даёт готовых к использованию сессионных токенов.
- Проверка на каждый запрос: хэшировать токен из cookie → найти `Session` по `tokenHash` →
  проверить `expiresAt` → подтянуть `User`. Сравнение — не по времени-зависимому `===` на
  сырых токенах (это защищено самим фактом, что сравнение идёт по индексированному хэшу в БД,
  а не наивным сравнением строк в JS, что тоже было бы уязвимо к timing-атакам при большом
  количестве попыток).

## 3. Регистрация

- **Преподаватель**: email, пароль, отображаемое имя → `User(role=teacher)` + `TeacherProfile`
  с временным `slug` → письмо с подтверждением email.
- **Ученик — по приглашению преподавателя** (ссылка/код с TTL). **[review-2]** Приглашение
  теперь работает в две ветки, т.к. ученик может уже существовать в системе (занимается у
  другого преподавателя):
  1. Email из приглашения не найден среди `User` → создаётся новый `User(role=student)` +
     `TeacherStudentLink` в статусе `active`.
  2. Email найден среди существующих `User(role=student)` → **новый `User` не создаётся**,
     создаётся дополнительная `TeacherStudentLink` для существующего пользователя (после
     подтверждения им приглашения — не автоматически, чтобы посторонний не мог "привязать"
     чужой email без согласия владельца аккаунта).
- **Admin**: не самостоятельная регистрация — создаётся вручную (seed/CLI).
- До подтверждения email — доступ read-only.

## 4. Вход

- Email + пароль → проверка `passwordHash` (Argon2id verify) → создание `Session` → cookie.
- Rate limiting: 5 неуспешных попыток / 15 минут на пару (IP, email) — см. `docs/SECURITY.md` §4.
- Блокировка — по связке (IP, email), не по аккаунту целиком (чтобы неуспешные попытки
  нельзя было использовать как DoS против конкретного чужого аккаунта).

## 5. Сессии — время жизни и отзыв

- TTL — например, 30 дней со скользящим продлением активности (обновление `expiresAt` при
  использовании, не создание новой строки на каждый запрос).
- Смена email/пароля/чувствительные действия — требуют повторного ввода пароля ("step-up"),
  не полагаются на возраст текущей сессии.
- Logout — удаление серверной записи `Session`. "Выйти со всех устройств" — массовое удаление
  `Session` по `userId`.
- Смена роли пользователя администратором инвалидирует все его сессии.
- Плановая очистка истёкших `Session`/`PasswordResetToken` — см. `docs/DATABASE.md` §7.

## 6. Восстановление пароля

- Запрос → `PasswordResetToken` (хэш токена в БД, как и у сессии) с TTL ~1 час → email →
  смена пароля инвалидирует все существующие `Session` пользователя.
- Rate limiting как на login.
- Ответ API не раскрывает, существует ли email в системе (защита от user enumeration).

## 7. RBAC на уровне сессии

- `session.userId` — единственное, что реально живёт в cookie/токене. `role` и `teacherId`
  **перечитываются из БД при каждой серверной проверке**, не кэшируются в самом токене —
  так смена роли администратором действует немедленно, а не только после переиздания токена.

## 8. Что НЕ делаем в MVP (сознательно, Правило 10 ТЗ)

- Google/любой OAuth как способ входа — см. §0.
- Multi-factor authentication (2FA) — таблица `Session` совместима с добавлением без миграции.
- Admin impersonation — не реализуется без конкретного support-сценария, см.
  `docs/MULTI_TENANCY.md` §5.

## 9. Если Auth.js всё же нужен позже

Если в будущем появится реальный (не гипотетический) сценарий множественных провайдеров
входа (например, продукт-оунер решает добавить вход через VK ID для российской аудитории) —
тогда пересмотр Auth.js оправдан, т.к. именно ради multi-provider абстракции он и создан.
До этого момента — не устанавливается (Правило 3 ТЗ — не добавлять зависимости без необходимости).
