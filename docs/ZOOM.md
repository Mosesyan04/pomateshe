# Pomateshe — Постоянные Zoom-ссылки

Статус: проектная архитектура. Требование ТЗ — "постоянные Zoom-ссылки", что специально
разобрано ниже как два разных по сложности и риску варианта.

## 1. MVP — статическая персональная ссылка (без Zoom OAuth)

- У каждого `TeacherProfile` есть поле `zoomPersonalLink` — сам преподаватель один раз
  создаёт в своём Zoom-аккаунте Personal Meeting Room (постоянная ссылка) и вставляет её в
  настройки кабинета.
- Приложение просто хранит и показывает эту ссылку ученикам, записанным на урок; при создании
  `Lesson` ссылка копируется в `Lesson.zoomLinkSnapshot`, чтобы история уроков не менялась
  задним числом, если преподаватель позже сменит ссылку.
- **Почему так в MVP**: удовлетворяет требование "постоянные ссылки" без интеграции с Zoom API
  и без хранения Zoom OAuth-токенов — меньше поверхность атаки, меньше зависимостей, полностью
  соответствует Правилу 10 ТЗ (минимально достаточно). Zoom-аккаунт при этом остаётся полностью
  под контролем преподавателя.
- Валидация — только формат URL (`https://*.zoom.us/...` или аналогично), без проверки, что
  ссылка "настоящая" (нет доступа к Zoom API в этом сценарии, и не нужен).

## 2. V2 (опционально, не в MVP) — Zoom OAuth / Server-to-Server интеграция

Если в будущем понадобится автосоздание встреч, синхронизация участников или отчётов о
посещаемости из Zoom:

- **Server-to-Server OAuth app** (не User-level OAuth) — подходит, если платформа создаёт
  встречи от имени преподавателя в рамках одного Zoom-аккаунта организации; если у каждого
  преподавателя свой независимый Zoom-аккаунт, нужен полноценный User OAuth поток, аналогичный
  Google Calendar (`docs/CALENDAR.md` §2) — с шифрованием токенов, `state`-проверкой,
  обработкой отзыва доступа.
- Каждый созданный через API митинг привязывается к `Lesson.calendarEventId`-подобному полю
  (потребует миграции схемы — добавление `zoomMeetingId` в `Lesson` при реализации V2).
- Риски идентичны Google Calendar OAuth (см. `docs/THREAT_MODEL.md` §5) — та же модель
  шифрования токенов и обработки сбоев применяется без изменений.

## 3. Явное решение

Архитектура закладывает MVP-вариант (§1) как единственный для первых фаз (`docs/ROADMAP.md`).
Переход на §2 — отдельное продуктовое решение, требующее отдельного аудита рисков перед
реализацией (новый OAuth-провайдер = новая поверхность атаки, см. `docs/SECURITY.md` §7).
