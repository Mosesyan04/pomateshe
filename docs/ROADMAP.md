## Phase 1 — Фундамент платформы

- Инициализация Next.js + TypeScript + Prisma проекта в `app/web` (структура — `docs/ARCHITECTURE.md` §4).
- Схема БД (`docs/DATABASE.md`) + миграции + RLS-политики с первой же миграции.
- Кастомный auth-модуль: регистрация/вход/сессии для всех трёх ролей (`docs/AUTH.md`,
  **[review-2]** больше не Auth.js — см. `docs/AUTH.md` §0).
- Плановая очистка истёкших `Session`/`PasswordResetToken` — cron-задача с первой фазы, не
  отложена (`docs/DATABASE.md` §7).
- Data-access layer + RBAC + ownership-проверки (`docs/MULTI_TENANCY.md`).
- `.gitignore`, `.env.example`, базовые security headers, rate limiting на auth (`docs/SECURITY.md`).
- Тесты изоляции тенантов с первого PR, не как "добавим позже" (`docs/TESTING.md` §2).

**Критерий готовности**: два преподавателя могут независимо зарегистрироваться, и тесты
подтверждают отсутствие пересечения их данных ни на уровне API, ни на уровне БД.

## Phase 2 — Кабинеты преподавателя и ученика: ядро

- Ученики, группы, приглашения.
- Расписание/занятия, статусы (проведён/отменён/неявка), учёт оплаты.
- Домашние задания + загрузка файлов (`docs/FILE_STORAGE.md`).
- Публичная страница преподавателя (SSR, `docs/DESIGN_SYSTEM.md`).
- Юридические страницы + cookie consent + согласия на ПДн (`docs/CONSENTS.md`) — обязательны
  до открытия регистрации внешним пользователям, не постфактум.

**Критерий готовности**: полный цикл "преподаватель добавил ученика → назначил урок → отметил
проведение и оплату → ученик увидел домашнее задание" работает end-to-end с реальными
серверными проверками доступа.

## Phase 3 — Realtime-доска

- Отдельный realtime-сервис (Yjs + WebSocket, `docs/WHITEBOARD.md`).
- Токены комнат, ограниченные участием в уроке.
- Автоматическая политика удаления досок (cron + retention).

**Критерий готовности**: доска работает совместно в реальном времени, недоступна пользователям
вне урока, автоматически удаляется по политике хранения — с тестом, подтверждающим удаление.

## Phase 4 — Интеграции

- Google Calendar OAuth + односторонняя синхронизация (`docs/CALENDAR.md`).
- Постоянные Zoom-ссылки, MVP-вариант без OAuth (`docs/ZOOM.md` §1).

**Критерий готовности**: занятия из Pomateshe появляются в Google Calendar преподавателя;
устаревший/отозванный токен приводит к явному уведомлению, а не тихому сбою.

## Phase 5 — Доходы и аналитика

- Отчёты по проведённым/неоплаченным занятиям, доходам за период.
- Экспорт данных (например, CSV) для преподавателя — не обязательно в Phase 2, т.к. требует
  накопленных данных за период, чтобы иметь смысл.

**Критерий готовности**: преподаватель видит корректную сводку доходов и список должников
по неоплаченным занятиям.

## Phase 6 — Замена текущего лендинга (опционально, по решению владельца продукта)

- `index.html` заменяется публичной страницей преподавателя новой платформы (или остаётся как
  отдельный маркетинговый сайт — решение вне этой архитектуры).
- Если заменяется — старый Google Apps Script backend (`docs/THREAT_MODEL.md` T-002) выводится
  из эксплуатации, а не остаётся параллельно работающим и всё ещё публично доступным.

## Будущие возможности (не планируются как отдельная фаза, но архитектура их не блокирует)

- Платежи (эскроу/приём онлайн-оплаты) — `Lesson`/`Payment`-модель в `docs/DATABASE.md`
  спроектирована так, чтобы добавление платёжного провайдера не требовало пересмотра схемы
  учёта занятий, только добавление таблицы `Payment` и вебхуков провайдера.
- Zoom OAuth V2, обратная синхронизация Google Calendar, 2FA, admin support-режим доступа —
  описаны как явно отложенные решения в соответствующих документах, не забытые пробелы.

## Открытые вопросы (требуют решения владельца продукта, не инженерные)

1. Финальный провайдер объектного хранилища/БД с дата-центром в РФ — зависит от бюджета.
   **[review-2]** Соответствие 152-ФЗ зависит не только от геолокации, но и от конкретного
   провайдера (договор обработки ПДн, организационные меры) — см. `docs/FILE_STORAGE.md` §2.1.
2. Итоговое решение по хостингу — зависит от результата чек-листа в `docs/DEPLOYMENT.md` §1;
   fallback-варианты на случай недоступности Docker/Node/WebSocket/Postgres зафиксированы в
   `docs/DEPLOYMENT.md` §1.1 и не требуют отдельного решения — решение нужно только по тому,
   какой из fallback-сценариев в итоге применяется.
3. Судьба текущего Google Apps Script backend и старого лендинга — держать, чинить точечно
   или полностью заменить в Phase 6. Рекомендуемые немедленные операционные шаги (не
   выполнялись, требуют вашего действия) — `docs/THREAT_MODEL.md` §"T-001/T-002 — Рекомендуемый
   порядок операционных действий".
4. Юридические тексты (оферта/политика) — нужен юрист или проверенный шаблон для 152-ФЗ и
   налогового статуса преподавателей (ИП/самозанятые), не пишутся инженерами "по аналогии" с
   чужих сайтов (Правило 5 ТЗ).
5. Точные значения retention-периода доски, лимитов файлов, TTL сессии — продуктовые константы,
   архитектура их не фиксирует жёстко.
