# Pomateshe — Стратегия тестирования

Статус: проектная стратегия, тесты не написаны в рамках этой задачи (нет кода приложения).

## 1. Пирамида тестирования

| Уровень | Что покрывает | Инструмент |
|---|---|---|
| Unit | Чистая бизнес-логика в data-access layer (расчёт цены, статусов, retention-дат) | Vitest |
| Integration | Route handlers/Server Actions поверх тестовой БД (реальный Prisma + Postgres в Docker) | Vitest + Testcontainers/локальный Postgres |
| E2E | Критичные пользовательские сценарии в браузере | Playwright |

Соотношение по объёму — больше unit/integration, минимум необходимых E2E (дорогие в поддержке
при одном разработчике) — Правило 10 ТЗ применимо и к тестовой стратегии.

## 2. Обязательные тесты изоляции тенантов (приоритет №1)

См. `docs/MULTI_TENANCY.md` §6-7 для полного обоснования каждого пункта. **[review-2]**
Список расширен по итогам второго архитектурного review — первая версия покрывала только
первые два пункта, что не поймало бы класс ошибок "RLS включён, но не действует" (см.
`docs/MULTI_TENANCY.md` §2.3).

1. **HTTP-уровень (было в v1)**: для каждого tenant-эндпоинта — "пользователь A аутентифицирован,
   пытается прочитать/изменить/удалить ресурс, принадлежащий B" → ожидаемый результат 403/404,
   не утечка данных в теле ответа даже при ошибке.
2. **RLS напрямую по SQL (было в v1)**, минуя приложение — подтверждает защиту на уровне БД
   независимо от кода приложения.
3. **Schema policy тест [review-2, новый]** — гоняется в CI на каждую миграцию, не вручную
   время от времени: SQL-запрос к `pg_tables`/`pg_policies`, подтверждающий для каждой
   tenant-таблицы `rowsecurity = true` **и** `forcerowsecurity = true`, и отдельно — что
   рантайм-роль (`pomateshe_app`) не входит в число владельцев ни одной из этих таблиц.
   Это единственный тест, ловящий сценарий "RLS включён, но обходится владельцем таблицы" —
   баг, который HTTP- и даже прямые SQL-тесты под неправильной ролью не поймают, если тестовое
   окружение тоже случайно использует роль-владельца.
4. **Fail-closed тест [review-2, новый]** — запрос к tenant-таблице под `pomateshe_app` без
   вызова `withTenantContext` вообще (переменная `app.current_teacher_id` не установлена)
   должен вернуть 0 строк, а не ошибку и не полный набор строк — подтверждает, что
   `current_setting(..., true)` действительно "закрывает", а не "открывает" доступ при
   отсутствии контекста.
5. **Конкурентный тест [review-2, новый]** — два параллельных запроса (симулирующих реальный
   Node.js event loop с общим пулом соединений) от двух разных преподавателей, использующих
   один и тот же connection pool, не должны видеть контекст/данные друг друга. Ловит класс
   багов "использован `SET` вместо `SET LOCAL`" или "контекст установлен вне транзакции" —
   именно тот сценарий, где баг проявляется только под конкурентной нагрузкой и не виден в
   последовательных тестах.
6. **Webhook-спуфинг тест [review-2, новый]** — входящий запрос на webhook-эндпоинт Google
   Calendar с валидным по формату, но не принадлежащим ни одному `CalendarIntegration`
   (или принадлежащим другому тенанту) `channelId` — должен быть отклонён (404/ignored), не
   привести к операциям от имени неверного `teacherId`.

Все шесть пунктов — часть CI gate, не опциональны, блокируют мердж при падении.

## 3. Тесты безопасности

- Rate limiting срабатывает на login/registration/password-reset (`docs/SECURITY.md` §4).
- CSRF-токен обязателен для мутирующих запросов вне Server Actions.
- Presigned URL для файлов не выдаётся без проверки ownership (`docs/FILE_STORAGE.md` §4).
- Токен комнаты доски не принимается realtime-сервисом после истечения TTL
  (`docs/WHITEBOARD.md` §3).

## 4. E2E-сценарии (Playwright, минимальный набор для MVP)

1. Регистрация преподавателя → подтверждение email → вход.
2. Приглашение ученика → регистрация ученика по ссылке → привязка к правильному `teacherId`.
3. Создание урока → отметка "проведён и оплачен" → отображение в отчёте по доходам.
4. Загрузка домашнего задания преподавателем → видимость только назначенному ученику.
5. Публичная страница преподавателя доступна без авторизации, кабинет — нет.
6. Cookie-баннер блокирует аналитику до согласия (`docs/CONSENTS.md` §3).

## 5. Тестовые данные

- Отдельная тестовая БД, поднимается в CI из чистой миграции (`prisma migrate deploy` на
  тестовую БД), не общая с dev/staging.
- Фикстуры — минимум двух преподавателей с пересекающимися по времени данными (специально
  для проверки изоляции, §2) — "один преподаватель, один ученик" недостаточно для тестов
  multi-tenancy. **[review-2]** Дополнительно нужен как минимум один ученик с двумя активными
  `TeacherStudentLink` у разных преподавателей одновременно — целевой сценарий для проверки,
  что ученик видит данные каждого преподавателя строго в рамках соответствующей связи и не
  может получить агрегированный "просмотр всех своих преподавателей сразу" ни по одной
  tenant-таблице, кроме `TeacherStudentLink` (см. `docs/MULTI_TENANCY.md` §3.2).
- Никаких реальных персональных данных в тестовых фикстурах (синтетические имена/email).

## 6. CI gate

- Lint + typecheck (TypeScript strict) + unit + integration тесты — обязательны на каждый PR.
- E2E — на PR в основную ветку и/или перед деплоем (может быть медленнее, не обязательно на
  каждый коммит в фиче-ветке).
- `npm audit`/Dependabot алерты — блокируют при критическом уровне (см. `docs/SECURITY.md` §10).

## 7. Что не покрывается в MVP

- Нагрузочное тестирование — добавляется при реальном росте нагрузки, не заранее
  (Правило 10 ТЗ), но архитектура realtime-сервиса и rate limiting уже закладывают базовую
  устойчивость (`docs/WHITEBOARD.md` §7, `docs/SECURITY.md` §4).
- Визуальное регрессионное тестирование UI — не в MVP, оценивается после появления
  стабильного дизайн-инвентаря (`docs/DESIGN_SYSTEM.md`).
