# Pomateshe — Хранение файлов

Статус: проектная архитектура, не реализовано.

## 1. Назначение

Домашние задания, материалы уроков, аватары преподавателей, снапшоты досок (см.
`docs/WHITEBOARD.md`) — изображения и файлы, загружаемые преподавателями и учениками.

## 2. Хранилище

- S3-совместимое объектное хранилище, провайдер с дата-центром в РФ (требование 152-ФЗ,
  см. §2.1 ниже и `docs/ARCHITECTURE.md` §8) — кандидаты для оценки на этапе реализации:
  Selectel S3, VK Cloud Object Storage, Yandex Object Storage. Итоговый выбор — после проверки
  цены/лимитов, не архитектурное решение этого документа.
- Файлы **не хранятся на диске веб-сервера** — диск контейнера эфемерен (пересборка/деплой
  стирает его), не масштабируется на несколько инстансов, сложно бэкапить отдельно от БД.
- Бакет приватный (без публичного ACL/listing) — доступ только через подписанные ссылки.

### 2.1 Соответствие 152-ФЗ — что архитектура даёт и чего не гарантирует **[review-2: новый раздел]**

Загружаемые файлы (домашние задания, снапшоты доски) — персональные данные ученика в той же
мере, что и записи в БД: почерк, ошибки, иногда личная информация в тексте работы. Требование
физического расположения в РФ (`docs/ARCHITECTURE.md` §8) распространяется на объектное
хранилище так же, как на PostgreSQL — это уже было явно сказано в §2 выше и не меняется.

**Важное уточнение, отсутствовавшее в первой версии документа**: геолокация дата-центра —
необходимое, но **не достаточное** условие соответствия 152-ФЗ. Архитектура фиксирует
требование "хранилище физически в РФ" как ограничение выбора провайдера, но **не может сама
по себе гарантировать юридическое соответствие** — это также зависит от:

- Статуса провайдера как оператора/обработчика персональных данных и наличия с ним договора
  на обработку ПДн (поручение обработки) — организационный, не архитектурный вопрос.
- Реальных организационных и технических мер защиты у конкретного провайдера (не только "ЦОД
  в России", но и его собственные практики доступа персонала, шифрования, аудита).
- Итогового юридического заключения по конкретному выбранному провайдеру — эта архитектура
  **не утверждает и не может утверждать соответствие 152-ФЗ** без такой проверки; это
  ответственность владельца платформы на этапе выбора провайдера, а не вывод, который можно
  сделать из документации.

Резервные копии объектного хранилища (версионирование/репликация) подчиняются тому же
требованию — см. `docs/DATABASE.md` §6, тот же принцип применяется и здесь: репликация в
зарубежный регион "для надёжности" недопустима, если она нарушает требование первичного
хранения в РФ.

## 3. Структура ключей

```
teachers/{teacherId}/materials/{materialId}/{originalFileName}
teachers/{teacherId}/avatars/{teacherId}.{ext}
teachers/{teacherId}/whiteboards/{whiteboardId}/snapshot.bin
```

**[Phase 3]** Ключ снапшота доски реализован как `.bin`, не `.json`, как было в первой версии
этого раздела — содержимое (`Y.encodeStateAsUpdate`) двоичное, оборачивать его в JSON
(base64) означало бы +33% к размеру объекта без всякой пользы. Ключ, что важнее,
**вычисляется детерминированно** из (`teacherId`, `whiteboardId`), а не хранится как случайный
идентификатор в `Whiteboard.snapshotStorageKey` (это поле убрано из схемы) — потому что
realtime-сервис, единственный писатель снапшотов, не имеет доступа к Postgres вообще
(`docs/WHITEBOARD.md` §2) и обязан быть способен вычислить свой собственный ключ без
какого-либо похода в БД, имея только claims из уже проверенного токена.

Префикс `teachers/{teacherId}/` — не механизм контроля доступа сам по себе (бакет приватный
в любом случае), но упрощает эксплуатационные задачи (bulk-удаление всех файлов тенанта при
запросе на удаление данных, см. `docs/CONSENTS.md`).

## 4. Загрузка (upload)

1. Клиент запрашивает `POST /api/uploads/presign` с метаданными (имя файла, MIME, размер,
   контекст — `homeworkId`/`lessonId`).
2. Сервер проверяет: пользователь имеет право загружать файл в этот контекст (ownership,
   см. `docs/MULTI_TENANCY.md`), MIME входит в allowlist, размер не превышает лимит
   (например, 25 МБ на файл — точное значение фиксируется продуктовым решением).
3. Сервер выдаёт presigned PUT URL с коротким TTL (например, 5 минут) и создаёт запись
   `MaterialFile` в статусе "ожидает загрузки".
4. Клиент грузит файл напрямую в хранилище, минуя сервер приложения (сервер не становится
   узким местом/вектором DoS через большие файлы, см. `docs/SECURITY.md` §8).
5. После успешной загрузки клиент уведомляет сервер (или сервер проверяет через webhook/HEAD
   запрос к объекту) — запись `MaterialFile` переводится в статус "готово".

## 5. Скачивание/просмотр

- Presigned GET URL с коротким TTL (например, 15 минут), выдаётся только после проверки, что
  текущий пользователь имеет право видеть этот файл (преподаватель-владелец контекста, либо
  ученик, для которого предназначено домашнее задание).
- Изображения для предпросмотра в UI — тот же механизм presigned GET, не публичный доступ.

## 6. Валидация типов файлов

- Allowlist MIME на основе содержимого (magic bytes через библиотеку определения типа), не
  только `Content-Type`/расширение из запроса клиента (оба подделываемы) — см.
  `docs/THREAT_MODEL.md` §3.
- Изображения: `image/jpeg`, `image/png`, `image/webp`. Документы: `application/pdf`, возможно
  офисные форматы — финальный список фиксируется продуктовым решением на этапе реализации.
- Исполняемые/скриптовые типы (`.exe`, `.sh`, `.html` с потенциальным JS) — запрещены безусловно.

## 7. Retention и удаление

- `MaterialFile` не удаляется автоматически по времени (в отличие от досок) — домашние задания
  и материалы имеют образовательную ценность на протяжении всего обучения.
- **[review-2]** Удаление — жёсткое (без `deletedAt`/"мусорной корзины" — первая версия этого
  документа и `docs/DATABASE.md` расходились: здесь было описано немедленное удаление, а схема
  в `docs/DATABASE.md` предполагала мягкое удаление; расхождение устранено в пользу простой
  модели без отдельного состояния "удалён, но восстановим" — это не заявленное требование ТЗ,
  добавлять его сейчас означало бы усложнять сверх необходимого, см. Правило 10 ТЗ).
- Удаление — при явном действии преподавателя/ученика, при удалении связанной сущности
  (например, каскадно при удалении `Homework`), или при запросе на удаление персональных
  данных (`docs/CONSENTS.md`) — во всех случаях удаление из БД и из объектного хранилища
  выполняется атомарно относительно друг друга (не оставляем "осиротевшие" файлы в хранилище):
  сначала удаляется объект в хранилище, затем строка в БД — если удаление объекта не удалось,
  строка не удаляется и операция считается не выполненной (не наоборот — иначе возможна
  "осиротевшая" запись без файла, что менее опасно, чем файл без учёта в БД, но всё равно
  нежелательно для отчётности о выполненных запросах на удаление персональных данных).

## 8. Антивирусная проверка (не в MVP)

- Сканирование загружаемых файлов антивирусом — не реализуется в MVP (нет прямого исполнения
  загруженных файлов на сервере, риск снижен presigned-подходом и allowlist MIME), но
  закладывается как возможное расширение пайплайна загрузки (шаг проверки перед переводом
  `MaterialFile` в статус "готово") при росте платформы — см. `docs/ROADMAP.md`.

## 9. Phase 2 — что реализовано и чем это отличается от §2-5 выше **[Phase 2]**

Домашние задания с одним фото-приложением на задание реализованы
(`src/server/homework.ts`, `src/app/api/files/[teacherId]/[materialFileId]/route.ts`) —
статус этого документа для этого случая уже не "не реализовано", но с двумя осознанными
отличиями от дизайна выше, оба задокументированы как временные в самом коде:

- **Хранилище — локальный диск, не S3** (`src/lib/files/local-disk-storage.ts`), по
  окружённым, а не архитектурным причинам: в этой среде разработки нет Docker и исходящий
  трафик блокирует даже скачивание локального S3-совместимого сервера для тестирования.
  Интерфейс (`saveFile`/`readStoredFile`/`deleteStoredFile` по opaque-ключу) специально
  спроектирован так, чтобы замена на реальный S3-адаптер не затронула ни `homework.ts`, ни UI.
- **Загрузка и отдача — не presigned URL, а прямой путь через сервер** (§4-5 выше описывают
  presign-модель для будущего S3): фото уходит в теле Server Action как `FormData` (Next.js
  Server Actions поддерживают `File` в `FormData` без отдельного upload-эндпоинта), а отдача —
  через `GET /api/files/[teacherId]/[materialFileId]` с обычной сессионной cookie-авторизацией,
  не подписанной ссылкой с TTL. Это осознанно для этого масштаба (нет CDN/кросс-доменной
  необходимости, файл и так same-origin) — при переходе на S3 презентованная выше presign-модель
  становится уместной и должна быть добавлена, а не то, что этот раздел её отменяет.
- Проверка владения (§5) реализована как есть: преподаватель видит свои файлы, ученик — только
  файлы заданий, выданных лично ему (проверка через `Homework.studentLinkId` →
  `TeacherStudentLink.studentUserId`, не через принадлежность к преподавателю вообще) — на
  каждый запрос, не только при выдаче ссылки. Проверено реальным browser-прогоном: другой
  преподаватель и посторонний ученик получают 404 при прямом обращении к чужому файлу по URL,
  неавторизованный запрос — 401.
- Валидация MIME (§6) реализована через собственную magic-byte проверку
  (`src/lib/files/detect-image-type.ts`) без новой зависимости — только три формата,
  относящихся к этому фото-кейсу (`jpeg`/`png`/`webp`), лимит размера — 10 МБ (продуктовая
  константа, см. `docs/ROADMAP.md` "Открытые вопросы" п.5).
