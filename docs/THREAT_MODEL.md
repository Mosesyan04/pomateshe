# Pomateshe — Модель угроз

Статус: результат аудита + проектный анализ для новой платформы. Формат: по каждому потоку —
угрозы (в духе STRIDE), сценарий атаки, мера защиты, ссылка на документ, где мера описана подробно.

## 0. Находки аудита существующего прототипа (`index.html`)

### T-001 — Обход аутентификации через захардкоженный master-PIN (КРИТИЧНО)

- **Где**: `index.html`, функция входа преподавателя (`if (pin === '7777' || pin === masterPin)`).
- **Сценарий**: независимо от того, какой PIN настроил преподаватель, PIN `7777` открывает
  полный доступ к панели преподавателя (все ученики, занятия, настройки).
- **Статус**: не исправляется в рамках этой задачи (правило "не менять функциональность без
  отдельного разрешения"), но это активная уязвимость в текущем публичном коде.
- **Рекомендация**: как минимум сменить/отключить дефолтный PIN на проде и рассмотреть точечный
  hotfix отдельным решением владельца продукта — до перехода на новую платформу
  (`docs/AUTH.md`).

### T-002 — Открытый backend-эндпоинт в публичном репозитории (КРИТИЧНО)

- **Где**: `index.html:981`, `DEFAULT_CLOUD_URL` — рабочий URL Google Apps Script Web App,
  видимый любому, кто откроет исходники страницы или историю Git.
- **Сценарий**: `GET {url}?action=load` отдаёт весь `db` (учеников, занятия, настройки,
  включая, возможно, `masterPin`, если он туда попадал); `POST` потенциально перезаписывает
  данные — зависит от реализации самого Apps Script (недоступна для аудита из этого репозитория).
- **Рекомендация**: считать URL скомпрометированным (он в истории Git навсегда, даже если
  убрать из HEAD) — перевыпустить Apps Script deployment с новым URL и/или добавить проверку
  секретного заголовка на стороне скрипта, до появления настоящего backend.

### T-001/T-002 — Рекомендуемый порядок операционных действий **[review-2: добавлено]**

Ниже — только рекомендации для владельца продукта. Ни один из шагов не выполнялся в рамках
этой задачи: у меня нет доступа к Google-аккаунту, в котором развёрнут Apps Script, а
`index.html` не изменяется без отдельного разрешения (в т.ч. смена самого `DEFAULT_CLOUD_URL`
на новый — это тоже изменение кода, а не только конфигурации, и требует того же разрешения).

Важное разграничение: **сам Apps Script (серверная логика за URL) не находится в этом
репозитории** — значит правки самого скрипта (не `index.html`) не подпадают под правило "не
менять существующий код без разрешения" применительно к этому Git-репозиторию, но это всё
ещё ваш production-сервис, который я не могу и не должен трогать без явного запроса — оценка
приведена как рекомендация, не как выполненное действие.

Рекомендуемая последовательность (самая эффективная мера — первая, закрывает сразу T-001 и T-002):

1. **Ограничить доступ к Apps Script Web App deployment**: в настройках развёртывания сменить
   "Who has access" с "Anyone"/"Anyone, even anonymous" на более узкую политику, или сразу
   архивировать текущее развёртывание (Manage deployments → Archive) — это немедленно "гасит"
   старый скомпрометированный URL независимо от того, что написано в `index.html`. Побочный
   эффект: текущий сайт перестанет получать/сохранять данные через этот URL, пока не заведён
   новый — это осознанный компромисс "временно недоступно" против "публично доступно на чтение/запись".
2. Если сайт должен продолжать работать — создать новое развёртывание с новым URL и добавить
   проверку секретного заголовка внутри самого Apps Script (это не даёт защиты сама по себе
   без обновления `index.html` новым URL — обновление `index.html` — отдельный шаг, требующий
   вашего разрешения на изменение кода).
3. PIN-баг (T-001) технически не устраняется шагами 1-2 сам по себе (баг в клиентском коде),
   но ограничение доступа к backend (шаг 1) резко снижает его практическую опасность — даже
   если кто-то войдёт через PIN `7777`, "войти" в чисто клиентское состояние без рабочего
   backend не даёт доступа к чужим данным.
4. Полноценное исправление — только через отдельно согласованное изменение `index.html`
   (замена PIN-логики) или через переход на новую платформу (`docs/ROADMAP.md`, Phase 1-2).

### T-003 — Отсутствие `.gitignore`

- **Где**: корень репозитория.
- **Риск**: при появлении кода приложения (env-файлы, ключи) без `.gitignore` высок риск
  случайного коммита секретов.
- **Мера**: создать `.gitignore` вместе с первым коммитом кода приложения (см. `docs/SECURITY.md` §7).
  Не создаётся в этой задаче, т.к. задача ограничена документацией.

## 1. Аутентификация и сессии

| Угроза | Сценарий | Мера |
|---|---|---|
| Spoofing | Подбор пароля / credential stuffing | Rate limiting, Argon2id, проверка утечек пароля (опционально, Have I Been Pwned API) |
| Spoofing | Кража session cookie через XSS | `httpOnly` cookie, строгий CSP (см. `docs/SECURITY.md` §5-6) |
| Elevation of Privilege | Подделка роли в клиентском запросе (`role: "admin"` в теле запроса) | Роль читается только из серверной сессии, никогда из тела запроса (`docs/AUTH.md`) |
| Repudiation | Пользователь отрицает действие (например, отмену урока) | `AuditLog` для чувствительных операций |

## 2. Multi-tenancy / изоляция данных

| Угроза | Сценарий | Мера |
|---|---|---|
| Information Disclosure | Забытый `WHERE teacherId = ...` в новом эндпоинте → утечка чужих учеников | Data-access layer как единственная точка запросов + PostgreSQL RLS как второй слой (`docs/MULTI_TENANCY.md`) |
| **[review-2]** Information Disclosure | Рантайм-роль БД приложения оказывается владельцем таблиц (обычная ситуация при "миграции и рантайм под одним DATABASE_URL") → RLS включён (`rowsecurity = true`), но **не действует**, т.к. владелец таблицы обходит RLS без `FORCE ROW LEVEL SECURITY` — приложение и тесты на уровне HTTP этого не заметят | Разделение ролей `pomateshe_migrator`/`pomateshe_app`, `FORCE ROW LEVEL SECURITY` на каждой tenant-таблице, отдельный schema-policy тест в CI (`docs/MULTI_TENANCY.md` §2.3, §6.4) |
| **[review-2]** Information Disclosure | `SET` (не `SET LOCAL`) или установка tenant-контекста вне транзакции → значение "утекает" на переиспользуемое из пула соединение и попадает в следующий, не связанный запрос другого пользователя | Только `withTenantContext` (`SET LOCAL` внутри `$transaction`) как единственная точка входа; конкурентный тест в CI (`docs/MULTI_TENANCY.md` §2.1, §6.5) |
| Tampering | Преподаватель A передаёт `studentId`/`studentLinkId` ученика преподавателя B в API | Ownership-проверка на каждой мутации до записи в БД |
| Information Disclosure | Ученик подключается к чужой доске, подобрав/угадав `whiteboardId` | Короткоживущий подписанный токен комнаты с серверной генерацией ID, выданный только после проверки участия в уроке (`docs/WHITEBOARD.md`) |
| Elevation of Privilege | Admin читает данные тенантов "по умолчанию" без аудита | Явный, залогированный support-режим через отдельную роль БД и отдельный connection pool (`docs/MULTI_TENANCY.md` §5) |
| **[review-2]** Information Disclosure | Webhook от Google Calendar с чужим/поддельным `channelId` резолвится не в того преподавателя | `teacherId` резолвится только через внутренний lookup `watchChannelId → CalendarIntegration`, не из тела webhook напрямую (`docs/MULTI_TENANCY.md` §7) |

## 3. Файлы

| Угроза | Сценарий | Мера |
|---|---|---|
| Tampering | Загрузка исполняемого файла под видом изображения (расширение подделано) | Проверка MIME по содержимому (magic bytes), не только по имени файла; allowlist типов |
| Denial of Service | Загрузка гигантских файлов исчерпывает диск/трафик | Лимит размера на уровне presigned URL и серверной проверки перед его выдачей |
| Information Disclosure | Публично читаемый бакет позволяет перечислить файлы других преподавателей | Приватные бакеты, только подписанные ссылки, непредсказуемые ключи (`docs/FILE_STORAGE.md`) |

## 4. Realtime-доска

| Угроза | Сценарий | Мера |
|---|---|---|
| Spoofing | Подключение к WebSocket без валидной сессии/токена комнаты | Проверка токена на handshake, не только на уровне HTTP до апгрейда |
| Denial of Service | Флуд событий доски от одного клиента (например, рекурсивный баг в клиенте) | Rate limiting на входящие сообщения на уровне realtime-сервиса, лимит размера сообщения |
| Tampering | Правки доски после того, как ученик покинул урок / доступ отозван | Периодическая ревалидация токена / TTL короче длительности урока с продлением |
| Information Disclosure | Доска не удаляется — накопление персональных данных сверх необходимого | Автоматическая политика удаления по `expiresAt` (`docs/WHITEBOARD.md`) |

## 5. Google Calendar / Zoom OAuth

| Угроза | Сценарий | Мера |
|---|---|---|
| Information Disclosure | Утечка `refresh_token` из БД → доступ к календарю преподавателя на неопределённый срок | Шифрование токенов at rest, отдельный ключ шифрования вне БД-бэкапа (`docs/SECURITY.md` §7) |
| CSRF | Подмена `state` параметра в OAuth callback | Проверка `state` (подписанный, с TTL) на каждый callback |
| Tampering | Открытый redirect через `redirect_uri` | Строгий allowlist `redirect_uri` на стороне Google Console и сервера |
| Availability | Устаревший refresh token (отозван пользователем в Google) молча ломает sync | Явная обработка ошибки refresh → уведомление преподавателя, а не тихий сбой (`docs/CALENDAR.md`) |

## 7. Масштабирование и доступность

| Угроза | Сценарий | Мера |
|---|---|---|
| Availability | Один инстанс приложения падает — весь сервис недоступен | Health-check + автоперезапуск (Docker restart policy) на MVP; горизонтальное масштабирование — по необходимости (`docs/ROADMAP.md`) |
| Availability | Пиковая нагрузка в начале учебного года | Мониторинг ресурсов, вертикальное масштабирование VPS как первый шаг (дешевле горизонтального для одного разработчика) |

## 8. Резервное копирование и удаление данных

| Угроза | Сценарий | Мера |
|---|---|---|
| Data Loss | Ошибочное массовое удаление (баг или неверная миграция) | Ежедневные бэкапы + мягкое удаление там, где применимо (`docs/DATABASE.md` §1, §6) |
| Compliance | Запрос на удаление персональных данных не выполняется полностью (остаются файлы/бэкапы) | Процедура удаления описана в `docs/CONSENTS.md`, включает объектное хранилище и график ротации бэкапов |

## 9. Приоритизация (для новой платформы, не прототипа)

Критично реализовать с первой фазы (Phase 1 в `docs/ROADMAP.md`): server-side RBAC + ownership
проверки, RLS, шифрование OAuth-токенов, presigned file access, rate limiting на auth-эндпоинтах.
Остальное — по мере появления соответствующего функционала (доска — Phase 3, интеграции — Phase 4).
