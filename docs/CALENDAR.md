# Pomateshe — Интеграция Google Calendar

Статус: проектная архитектура, не реализовано.

## 1. Назначение

Преподаватель привязывает свой Google Calendar, занятия из Pomateshe отражаются в нём
(и, опционально, наоборот) — снижает ручную работу и риск накладок в расписании преподавателя,
если он ведёт часть занятий вне платформы.

## 2. OAuth-поток (отдельный от входа в платформу)

- Инициируется из настроек кабинета преподавателя, не из формы логина (см. `docs/AUTH.md` §1).
- Scope — минимально необходимый: `https://www.googleapis.com/auth/calendar.events`
  (не полный доступ к календарю, если события — единственное, что нужно).
- `state`-параметр — подписанный, с TTL, проверяется на callback (защита от CSRF в OAuth-потоке,
  см. `docs/THREAT_MODEL.md` §5).
- `redirect_uri` — фиксированный, из allowlist в Google Console и на сервере.
- Полученные `access_token`/`refresh_token` шифруются (AES-256-GCM) перед записью в
  `CalendarIntegration` (см. `docs/SECURITY.md` §7) — обычная БД-запись в открытом виде
  недопустима, т.к. это ключ к личному календарю преподавателя на неопределённый срок.

## 3. Направление синхронизации

- **Источник истины — Pomateshe.** `Lesson` создаётся/меняется в приложении → приложение
  создаёт/обновляет/удаляет соответствующее событие в Google Calendar, помечая его
  `extendedProperties.private.pomatesheLessonId` для сопоставления.
- Обратная синхронизация (изменение события в Google Calendar → изменение `Lesson`) —
  опциональная возможность второй фазы, не обязательна для MVP: усложняет разрешение
  конфликтов (что "выигрывает", если правки одновременно с двух сторон). Если реализуется —
  строго через `watch`-канал (push-уведомления), не постоянный polling.
- MVP: одностороннее уведомление о рассинхроне — если событие в Google Calendar пропало/изменено
  в обход приложения, преподавателю показывается предупреждение при следующем открытии урока,
  без автоматической перезаписи в любую сторону без подтверждения пользователя.

## 4. Обработка сбоев

- Access token истёк → приложение использует `refresh_token` для обновления. Если и
  `refresh_token` невалиден (пользователь отозвал доступ в Google Account) — интеграция
  помечается `disabled`, преподавателю показывается явное уведомление с предложением
  переподключить, **не тихий сбой** (см. `docs/THREAT_MODEL.md` §5).
- Google API rate limit/недоступность — синхронизация с календарём не блокирует основную
  операцию (создание урока в Pomateshe всегда успешно, синхронизация с календарём — best-effort
  с ретраями в фоне, не в теле HTTP-запроса пользователя).

## 5. Данные, которые уходят в Google

- В событие календаря попадают только необходимые поля (время, предмет/название, ссылка на
  Zoom, если применимо) — не переносится личная история ученика/заметки преподавателя.
  Минимизация данных, отправляемых во внешний сервис.

## 6. Что не делается в MVP

- Импорт "внешних" событий из Google Calendar как источник занятости (busy/free) для
  автоматического планирования — полезная, но не обязательная фича; не усложняем модель
  данных сейчас (Правило 10 ТЗ).

## 7. Реализовано на данный момент

Статус выше ("проектная архитектура, не реализовано") относится только к разделам 2–5
(собственно OAuth и синхронизация с Google). Пользовательский календарь как таковой — уже
реализован, независимо от подключения Google:

- `/teacher/calendar` и `/student/calendar` — недельный (по умолчанию), дневной и месячный вид,
  переключение — обычные `<Link>` с query-параметрами `view`/`date`, без клиентского роутинга.
  Расчёт границ периода и сетки дней/недель — чистые функции без побочных эффектов
  (`src/lib/calendar/view-range.ts`, `build-grid-data.ts`), покрыты юнит-тестами отдельно от БД.
- Перетаскивание (drag-and-drop) — самодельное, на Pointer Events API (не HTML5 DnD, у него нет
  поддержки touch), т.к. это единственное требование задачи, ради которого сетка вообще стала
  клиентским островом. Правило доступа — "кто поставил урок/событие, тот и двигает": уроки
  создаёт только преподаватель → двигает только преподаватель (`Lesson.editable: true` только
  на `/teacher/calendar`, у ученика те же уроки — `editable: false`, попытка вызвать action
  напрямую в обход UI отклоняется на сервере, см. `rescheduleLessonForbiddenAction` в
  `src/app/student/calendar/actions.ts`); личные события двигает только их владелец
  (RLS `owner_only`, см. `docs/MULTI_TENANCY.md` §4.4).
  Найденный при реализации баг (не архитектурный, но зафиксирован — обнаружен только реальным
  browser-прогоном, не тайпчеком и не юнит-тестом): при перетаскивании элемента в другую
  колонку/ячейку дня нельзя условно "не рендерить" его в исходном месте — DOM-узел, на котором
  вызван `setPointerCapture`, не должен размонтироваться до `pointerup`, иначе браузер молча
  теряет все дальнейшие события указателя для этого жеста. Оба грида (`time-grid.tsx` —
  неделя/день, `month-grid.tsx` — месяц) держат перетаскиваемый элемент смонтированным в его
  исходной колонке/ячейке весь жест и визуально следуют за курсором через `position: fixed`,
  считая итоговую дату/время только в момент отпускания.
- Личные (не-урочные) события календаря — своя модель `PersonalCalendarEvent`, доступна и
  преподавателю, и ученику, полностью приватна (не видна второй стороне), см.
  `docs/MULTI_TENANCY.md` §4.4 про новый вид tenant-контекста (`userId`, не `teacherId`/
  `studentUserId`) для данных, принадлежащих пользователю независимо от роли.
- Ещё не сделано (раздел 2–5 этого документа, Phase 4 в `docs/ROADMAP.md`): само подключение
  Google-аккаунта и синхронизация — календарь выше работает полностью автономно от Google уже
  сейчас, подключение Google добавит к нему одностороннюю зеркальную запись, не изменяя UI.
