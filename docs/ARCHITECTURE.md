# Pomateshe — Архитектура платформы

Статус: черновик архитектуры (Phase 0, документация без реализации).
Дата аудита: 2026-09-10.

## 1. Контекст и цели

Pomateshe — multi-tenant платформа для репетиторов (преподавателей) и их учеников:
публичные страницы преподавателей, личные кабинеты, расписание, домашние задания,
учёт занятий и доходов, realtime-доска, интеграции с Google Calendar и Zoom.

Ключевое архитектурное ограничение, заданное владельцем продукта: **систему поддерживает
один разработчик**. Отсюда — приоритет на модульный монолит, минимум движущихся частей,
managed-сервисы вместо самостоятельно эксплуатируемой инфраструктуры там, где это возможно.

Второе ключевое ограничение: домен `pomateshe.ru` и русскоязычная аудитория означают, что
персональные данные российских пользователей подпадают под 152-ФЗ «О персональных данных» —
это влияет на выбор хостинга и БД (см. §8 и `docs/CONSENTS.md`, `docs/SECURITY.md`).

## 3. Выбранный стек (to-be) и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Язык | TypeScript (строгий режим) везде — frontend, backend, скрипты | Один язык для всей команды из одного разработчика, общие типы между клиентом и сервером |
| Web-фреймворк | Next.js (App Router), self-hosted Node-сервер (не static export) | SSR/ISR нужен для публичных страниц преподавателей (SEO), Route Handlers закрывают REST-подобный API, Server Actions — для форм кабинета. Не привязываемся к Vercel — деплоим как обычный Node-процесс в Docker, что важно при неопределённости с хостингом |
| ORM/БД-доступ | Prisma + PostgreSQL 15+ | Строгая типизация схемы, миграции как код, хорошая поддержка PostgreSQL RLS через `$executeRaw` для `SET LOCAL` |
| База данных | PostgreSQL (managed либо в контролируемом контейнере) | Реляционная модель подходит для учеников/групп/занятий/платежей; нативная Row-Level Security — второй слой изоляции тенантов (см. `docs/MULTI_TENANCY.md`) |
| Аутентификация | Кастомная минимальная сессионная модель (email+пароль, Argon2id, хэшированный токен в `Session`) — **[review-2]** не Auth.js, см. `docs/AUTH.md` §0 | DB-сессии дают возможность отзывать доступ; своя реализация без неиспользуемой OAuth-как-логин машинерии — Google OAuth в системе нужен только для Calendar-интеграции (`docs/CALENDAR.md`), не для входа |
| Realtime / доска | Yjs (CRDT) + собственный WebSocket-сервис на Node (`ws`) | CRDT снимает часть проблем конфликтов правок на доске; WebSocket-процесс маленький и однозначно необходим — HTTP-хостинг без long-lived-соединений (многие "serverless" площадки) не подходит для доски |
| Файловое хранилище | S3-совместимое объектное хранилище (провайдер РФ, см. §8) | Файлы не должны жить на диске веб-сервера — не переживут пересборку контейнера, не масштабируются, сложно бэкапить |
| Фоновые задачи | `node-cron` внутри процесса приложения ИЛИ системный cron, дёргающий защищённый internal endpoint | Отдельный планировщик/очередь (BullMQ+Redis) — избыточна на объёмах одного репетитора-платформы; добавляется по необходимости (см. `docs/ROADMAP.md`) |
| Инфраструктура | Docker Compose: `app` (Next.js custom server + WS upgrade), `postgres` (если не managed), опционально `redis` (rate limiting / pub-sub при масштабировании) | Воспроизводимый деплой одним `docker compose up`, посилен для одного разработчика |
| Reverse proxy / TLS | Caddy (автоматический TLS) либо nginx, если хостинг требует | Терминация HTTPS, редирект www→apex, security headers |

### Отклонённые/отложенные варианты и почему

- **Полный serverless (Vercel Functions/Edge)** — отклонён как основная платформа: WebSocket-доска
  и длительные операции (sync с Google Calendar) плохо ложатся на serverless-таймауты;
  сам Next.js при этом всё равно используется, но в self-hosted Node-режиме.
- **Supabase/Firebase как BaaS** — отложено: удобно для MVP, но плохо совместимо с требованием
  строгой изоляции тенантов через собственный RLS-слой под полным контролем и с 152-ФЗ
  (нужен явный контроль над локацией данных).
- **Микросервисы/Kubernetes** — избыточны по правилу "один разработчик" (см. Правило 10 ТЗ).
  Модульный монолит + один маленький realtime-сервис — минимально достаточная архитектура.
- **MongoDB/NoSQL** — данные платформы существенно реляционные (ученики↔группы↔занятия↔оплаты),
  PostgreSQL с точки зрения целостности данных и отчётности (доходы/аналитика) подходит лучше.

## 5. Архитектура frontend

- Next.js App Router, три сегмента маршрутов:
  - `(public)` — страницы преподавателей (`/[teacherSlug]`), юридические страницы, вход/регистрация. SSR/ISR, без клиентского состояния, доступны без авторизации.
  - `(teacher)` — личный кабинет преподавателя. Защищён middleware, требует роль `teacher`.
  - `(student)` — личный кабинет ученика. Защищён middleware, требует роль `student`.
- Общий UI-слой строится по принципам из установленных skills `ui-ux-pro-max` и
  `design-taste-frontend` (см. `docs/DESIGN_SYSTEM.md`) — применяется на этапе реализации,
  не в этой задаче.
- Состояние: серверные компоненты + минимум клиентского состояния; для доски — отдельный
  клиентский provider с Yjs-документом и WebSocket-подключением.
- Middleware проверяет сессию и роль **только для UX** (редиректы) — все реальные проверки
  доступа дублируются на сервере при каждом запросе к данным (Правило 8 ТЗ: не полагаться
  только на frontend-проверки).

## 6. Архитектура backend

- Backend живёт внутри Next.js (`app/api/**` route handlers + Server Actions) — отдельного
  REST-сервиса нет, чтобы не плодить сущности для одного разработчика.
- **Data-access layer**: весь доступ к tenant-scoped таблицам идёт через сервисные функции
  в `src/server/*`, которые принимают `session` и сами подставляют `teacherId` в запрос.
  Route handlers и Server Actions никогда не строят Prisma-запросы к tenant-таблицам напрямую.
  Это единая точка, где enforced multi-tenancy (детали — `docs/MULTI_TENANCY.md`).
- Realtime-доска обслуживается отдельным Node-процессом (`app/realtime`), т.к. WebSocket
  плохо уживается с Next.js request-response моделью под многими хостингами. Процесс
  авторизует подключение по короткоживущему токену, выданному основным приложением после
  проверки прав (детали — `docs/WHITEBOARD.md`).
- Внешние интеграции (Google Calendar, Zoom) изолированы в `src/lib/integrations/*` со своим
  слоем шифрования токенов (детали — `docs/CALENDAR.md`, `docs/ZOOM.md`, `docs/SECURITY.md`).

## 7. Ключевые системные потоки (на уровне обзора)

1. **Публичная страница преподавателя** → SSR по `teacherSlug` → только публично-безопасные поля.
2. **Регистрация/вход** → кастомный auth-модуль (`docs/AUTH.md`) → создание `User` +
   (для teacher) `TeacherProfile`, (для student) `TeacherStudentLink` → DB-сессия.
3. **Создание занятия** → Server Action в кабинете преподавателя → data-access layer проверяет
   `teacherId === session.teacherId` для ученика/группы → запись `Lesson` → (опционально) sync
   в Google Calendar.
4. **Урок на доске** → клиент запрашивает у API токен комнаты (проверка, что пользователь —
   преподаватель этого урока или назначенный ученик) → подключение к realtime-сервису по токену.
5. **Загрузка файла ДЗ** → API выдаёт presigned PUT URL в объектное хранилище (после проверки
   владения) → клиент грузит напрямую в хранилище → метаданные сохраняются в БД.
6. **Плановая очистка** → cron дёргает internal endpoint → удаление досок старше retention-периода,
   напоминания о неоплаченных занятиях (детали — `docs/WHITEBOARD.md`, `docs/ROADMAP.md`).

## 8. Хостинг — чек-лист закрыт **[обновлено: финальный ответ поддержки SprintHost]**

Поддержка SprintHost подтвердила: постоянный Node.js-процесс — да, WebSocket — да (включая
долгоживущие соединения для realtime-доски, см. ниже), PostgreSQL — да, SSH-доступ — есть,
серверы в РФ — да, cron — да. Docker явно не упоминался (вероятно недоступен, деплой
планируется через нативный `systemd`/PM2, а не Docker Compose). Стек в §3 и Сценарий A в
`docs/DEPLOYMENT.md` §2 — подтверждённый рабочий план, единственный активный сценарий, не
гипотеза с двумя ветками.

Лимит «6 обработчиков запросов на одном веб-сервере», который изначально был открытым
вопросом, — **закрыт**: по финальному ответу поддержки WebSocket-соединение обычно не занимает
один из 6 обработчиков на всё время, пока оно открыто ("зависит от реализации, но вообще нет").
Realtime-сервис доски размещается на том же сервере SprintHost, отдельный VPS не требуется.
Оговорка "зависит от реализации" означает, что перед реальным запуском доски пользователям
обязательно нагрузочное тестирование на самом SprintHost (много одновременных долгих
WebSocket-соединений) — не блокирует старт Фазы 1 (доска — Phase 3), но обязательно перед
Phase 3 exit. VPS-вариант остаётся задокументированным запасным планом на случай, если
нагрузочное тестирование выявит проблему — подробности и обе трактовки лимита (для истории
решения) — `docs/DEPLOYMENT.md` §1a.

Отдельно: персональные данные российских учеников/преподавателей — по 152-ФЗ первичное
хранение должно быть на серверах в РФ. Подтверждённое расположение серверов SprintHost в РФ
закрывает это требование для основного сценария (всё на SprintHost); если запасной VPS-план
для realtime когда-либо будет задействован, тот провайдер тоже должен быть РФ-региона — это
ограничение не снимается независимо от итогового решения по размещению.
