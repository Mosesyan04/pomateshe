# Pomateshe — Модель безопасности

Статус: проектные требования, обязательны к реализации с первой фазы (не "добавим позже").

## 1. Принципы (сквозные для всей системы)

1. **Server-side authorization всегда, frontend-проверки — только UX.** Каждый route handler
   и Server Action самостоятельно проверяет сессию, роль и владение ресурсом. Наличие проверки
   в middleware или в клиентском коде не освобождает от серверной проверки.
2. **Deny by default.** Нет сессии/роли/владения → 401/403, без исключений "для удобства".
3. **Каждый tenant-запрос проходит через data-access layer**, который подставляет `teacherId`
   (см. `docs/MULTI_TENANCY.md`) — прямые Prisma-запросы к tenant-таблицам вне этого слоя
   запрещены код-ревью правилом.
4. **Секреты не попадают в репозиторий.** `.env.example` содержит только имена переменных.
   Реальные значения — в secret-хранилище хостинга/CI. `.gitignore` обязателен с первого
   коммита кода приложения (см. §7).

## 2. Аутентификация и сессии

Подробная модель — `docs/AUTH.md`. Кратко:

- Пароли — Argon2id, не bcrypt (устойчивее к GPU-перебору при равных параметрах).
  **[review-2]** Аутентификация — кастомная минимальная модель, не Auth.js (см. `docs/AUTH.md`
  §0 для обоснования пересмотра).
- Сессии — серверные (таблица `Session`, хэш токена, не сырой токен), не голый JWT: позволяет
  отзывать сессии (компрометация устройства, смена пароля, блокировка аккаунта администратором).
- Cookie сессии: `httpOnly`, `secure` (в проде), `sameSite=lax` (не `none`), с коротким TTL
  и скользящим продлением.
- Rate limiting на login/registration/password-reset (см. §4).
- Email verification обязателен перед выдачей полного доступа к личному кабинету.

## 3. RBAC (Role-Based Access Control)

- Роли: `admin`, `teacher`, `student` — хранятся в `User.role`, неизменяемы клиентом.
- Смена роли — только через административный процесс с записью в `AuditLog`.
- Авторизация состоит из двух проверок, обе обязательны:
  1. **Ролевая** — может ли роль вообще выполнять действие (например, только `teacher` создаёт `Lesson`).
  2. **Ресурсная (ownership)** — принадлежит ли конкретный ресурс текущему пользователю/тенанту
     (например, `teacher` может редактировать только свои `Lesson`, `student` — видеть только
     свои домашние задания).
- `admin` не имеет "суперправа читать всё молча" — кросс-тенантный доступ администратора
  логируется в `AuditLog` и ограничен конкретными поддерживаемыми сценариями (см.
  `docs/MULTI_TENANCY.md` §"Доступ администратора").

## 4. Rate limiting

| Эндпоинт | Лимит (ориентир) | Ключ |
|---|---|---|
| `POST /api/auth/login` | 5 попыток / 15 мин | IP + email |
| `POST /api/auth/register` | 3 / час | IP |
| `POST /api/auth/password-reset` | 3 / час | IP + email |
| Мутации API в целом | 60 запросов / мин | userId |
| Загрузка файлов | 20 / мин | userId |
| WebSocket подключение к доске | 10 подключений / мин | userId |

Для single-instance деплоя достаточно in-memory лимитера (например, `lru-cache`-based) —
Redis подключается только при горизонтальном масштабировании (несколько инстансов приложения),
см. `docs/ROADMAP.md`. Ограничение должно быть реализовано с первой фазы, не отложено.

## 5. Защита от типовых веб-угроз

- **SQL injection** — исключается использованием Prisma (параметризованные запросы). Сырой
  SQL (`$queryRaw`) допускается только для `SET LOCAL app.current_teacher_id` и подобных
  системных операций, всегда через параметризованные вызовы Prisma, никогда через конкатенацию строк.
- **XSS** — React экранирует вывод по умолчанию. Единственное место, где возможен rich-text
  (описание домашнего задания, bio преподавателя), рендерится через санитайзер (DOMPurify
  на сервере перед сохранением ИЛИ при рендере) с allowlist тегов. `dangerouslySetInnerHTML`
  запрещён без санитайзера — правило код-ревью.
- **CSRF** — **[review-2]** без Auth.js весь CSRF-периметр — наша ответственность (в первой
  версии документа часть периметра ошибочно считалась закрытой библиотекой). Для мутирующих запросов:
  double-submit cookie токен + проверка `Origin`/`Referer` на сервере для всех
  state-changing запросов (POST/PUT/PATCH/DELETE), т.к. `sameSite=lax` не закрывает все сценарии.
- **Clickjacking** — `X-Frame-Options: DENY` / `frame-ancestors 'none'` в CSP.
- **Открытые редиректы** — валидация `callbackUrl` в auth-потоке по allowlist собственного домена.
- **IDOR** — закрывается ownership-проверкой в data-access layer (§3), а не "угадыванием по ID":
  ID сами по себе не являются секретом (cuid2 непредсказуем, но это defense-in-depth, не замена проверке).

## 6. HTTP security headers (через middleware/reverse proxy)

**[Phase 1: реализовано]** в `src/proxy.ts`, применяется к каждому запросу страницы.

- `Content-Security-Policy` — строгий, без `unsafe-inline` для скриптов (per-request nonce +
  `strict-dynamic`). Для `style-src` — **не** nonce-based, а `'unsafe-inline'`: найдено при
  реализации, что CSP-nonce работает только для элементов `<script>`/`<style>`, но не для
  инлайн-атрибута `style="..."`, а страницы Phase 1 написаны с `style={{...}}` (JSX-проп,
  рендерится как раз в этот атрибут). К тому же по спеке CSP3 наличие nonce-source в
  директиве заставляет браузер игнорировать `'unsafe-inline'` в той же директиве — то есть
  указать оба сразу для `style-src` не просто бесполезно, а тихо отключает защиту с обеих
  сторон одновременно. Когда Phase 2 (`docs/DESIGN_SYSTEM.md`) уберёт инлайн-стили в пользу
  CSS Modules/Tailwind-классов, `style-src` можно будет перевести на nonce и убрать
  `unsafe-inline` — до этого момента это осознанный, документированный компромисс, не пробел.
- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`.
- `X-Content-Type-Options: nosniff`.
- `Referrer-Policy: strict-origin-when-cross-origin`.
- `Permissions-Policy` — отключить неиспользуемые API (camera, microphone, geolocation),
  кроме страницы доски, если понадобится (не планируется в MVP).
- `X-Frame-Options: DENY` — добавлено сверх исходного списка как дублирующая защита к
  `frame-ancestors` в CSP (см. §5 "Clickjacking") для браузеров без поддержки `frame-ancestors`.

Nonce-based CSP требует динамического рендеринга каждой страницы, на которую применяется
(иначе билд-тайм HTML не может содержать per-request nonce) — все страницы Phase 1 уже были
динамическими (читают `cookies()`/`searchParams`), кроме `/`, которую пришлось явно перевести
на динамический рендеринг (`connection()` из `next/server`) специально из-за этого.

## 7. Управление секретами

- `.gitignore` создаётся вместе с первым коммитом кода приложения и включает как минимум:
  `.env`, `.env.*.local`, `node_modules/`, `.next/`, `*.pem`, `*.key`.
- Секреты окружения: `DATABASE_URL`, `AUTH_SECRET`, `GOOGLE_CLIENT_ID/SECRET`,
  `S3_*`, `TOKEN_ENCRYPTION_KEY`, `INTERNAL_CRON_SECRET` — живут только в secret-хранилище
  хостинга/CI, не в репозитории, не в логах.
- **Шифрование секретов интеграций** (OAuth refresh/access токены Google, будущие Zoom-токены):
  AES-256-GCM с ключом `TOKEN_ENCRYPTION_KEY`, который сам не хранится в БД и ротируется
  отдельно от БД-бэкапов. Никогда не логировать значения токенов, даже в debug-режиме.
- Ротация: `AUTH_SECRET` и `TOKEN_ENCRYPTION_KEY` — процедура ротации описывается перед
  выходом в прод (инвалидирует все сессии/потребует переавторизации интеграций — приемлемо
  для планового события, документируется в runbook на этапе реализации).

## 8. Загрузка файлов

- Presigned URL — клиент никогда не проксирует бинарные данные через Next.js сервер
  (иначе сервер становится узким местом и вектором DoS через большие файлы).
- Серверная проверка перед выдачей presigned URL: allowlist MIME-типов, максимальный размер,
  принадлежность `lessonId`/`homeworkId` текущему пользователю.
- Хранилище — приватные бакеты, доступ только через короткоживущие подписанные ссылки на
  чтение (не публичные ACL). Подробности — `docs/FILE_STORAGE.md`.

## 9. Логирование и мониторинг

- Структурированные логи (JSON), без PII в теле лога (email — можно, пароли/токены — никогда).
- Security-события (неуспешные входы сверх порога, смена роли, admin cross-tenant доступ,
  массовое удаление) пишутся в `AuditLog` и, опционально, во внешний мониторинг (Sentry/аналог)
  на более поздней фазе.
- Алертинг на аномалии (например, резкий рост 403/401) — добавляется по мере роста нагрузки,
  не блокирует MVP.

## 10. Зависимости и supply chain

- `npm audit` / Dependabot (или аналог) в CI — блокирует мердж при критических уязвимостях
  в прямых зависимостях.
- Минимизация числа зависимостей (Правило 10 ТЗ) — каждая новая зависимость обосновывается
  в PR, а не добавляется "на всякий случай".
