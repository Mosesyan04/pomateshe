# Pomateshe — Multi-tenancy и изоляция данных

Статус: проектная модель, пересмотрена во втором архитектурном review (см. `docs/ROADMAP.md`,
Phase 0.2). Это самый критичный документ архитектуры — нарушение изоляции означает утечку
персональных данных учеников между преподавателями, что недопустимо как по продуктовым, так
и по юридическим (152-ФЗ) причинам.

> **Изменение относительно первой версии**: ученик теперь может в будущем заниматься у
> нескольких преподавателей (см. §1.1) — это меняет модель тенанта для одной конкретной
> таблицы (`TeacherStudentLink`) и требует отдельного объяснения (§3.2). Также добавлен
> критический для корректности RLS момент — владение таблицами в Postgres (§2.3), которого не
> было в первой версии документа и который при реализации "в лоб" **сделал бы RLS
> недействующим незаметно для тестов на уровне приложения**.

## 1. Модель тенанта

- **Тенант = преподаватель** (`TeacherProfile`). Все данные, кроме публичной страницы
  преподавателя и справочных/юридических страниц, принадлежат ровно одному тенанту.
- `admin` — не тенант, а платформенная роль с ограниченным, аудируемым доступом (см. §5).

### 1.1 Ученик — не тенант, но и не привязан жёстко к одному тенанту

Ученик (`User` с `role=student`) — самостоятельная идентичность, независимая от преподавателя.
Связь ученика с конкретным преподавателем — отдельная сущность `TeacherStudentLink`
(many-to-many между `User` и `TeacherProfile`, подробности схемы — `docs/DATABASE.md` §2).
Один и тот же ученик может иметь несколько активных `TeacherStudentLink` у разных
преподавателей одновременно — платформа не ограничивает это с первой фазы (это была ошибка
первой версии документа, зафиксированная как "допущение MVP"; ошибка исправлена здесь и в
`docs/DATABASE.md`, `docs/AUTH.md`).

Важное следствие: **все данные ученика (заметки, ДЗ, оценки) всё равно принадлежат ровно
одному тенанту** — тенант данных определяется не самим учеником, а конкретной связью
`TeacherStudentLink`, к которой они привязаны. `Lesson`, `Homework`, `MaterialFile` и т.д.
ссылаются на `TeacherStudentLink.id`, а не напрямую на `User.id` ученика — это сохраняет
"один тенант на строку" инвариант для всех таблиц, кроме самой `TeacherStudentLink` (см. §3.2).

## 2. Стратегия изоляции — два независимых слоя

Полагаться только на один слой недопустимо (Правило 8 ТЗ — не полагаться только на
frontend-проверки распространяется и на "полагаться только на один backend-слой").

### 2.1 Слой 1 — Data-access layer (обязательная точка входа)

Единственный способ прочитать/изменить tenant-таблицу — вызвать сервисную функцию, обёрнутую
в `withTenantContext`:

```ts
// src/server/tenant-context.ts
async function withTenantContext<T>(
  ctx: { teacherId?: string; studentUserId?: string },
  fn: (tx: PrismaTransactionClient) => Promise<T>
): Promise<T> {
  return prisma.$transaction(async (tx) => {
    // ПАРАМЕТРИЗОВАННЫЙ вызов, НЕ конкатенация строк — teacherId/studentUserId
    // приходят из проверенной серверной сессии, но параметризация обязательна
    // как defense-in-depth (см. docs/SECURITY.md §5, SQL injection).
    if (ctx.teacherId) {
      await tx.$executeRaw`SELECT set_config('app.current_teacher_id', ${ctx.teacherId}, true)`;
    }
    if (ctx.studentUserId) {
      await tx.$executeRaw`SELECT set_config('app.current_student_user_id', ${ctx.studentUserId}, true)`;
    }
    return fn(tx);
  });
}

// Пример использования в data-access layer:
export function getLessonsForTeacher(session: TeacherSession, filters: LessonFilters) {
  return withTenantContext({ teacherId: session.teacherId }, (tx) =>
    tx.lesson.findMany({ where: { teacherId: session.teacherId, ...filters } })
  );
}
```

Route handlers/Server Actions **не вызывают `prisma.*` напрямую** — только функции из
`src/server/*`, которые сами оборачивают вызов в `withTenantContext`. Это blocking-правило
код-ревью (проверяется вручную на этапе реализации, т.к. кода нет в этой задаче).

**Почему транзакция, а не просто `$executeRaw` перед запросом**: `SET LOCAL`
(через `set_config(..., true)`) действует только до конца текущей транзакции — это критично
при пуле соединений. Prisma переиспользует физические соединения к Postgres между запросами;
если установить `app.current_teacher_id` **вне** транзакции (обычным `SET`, не `SET LOCAL`,
или через `$executeRaw` без последующего `$transaction`), значение осядет на переиспользуемом
соединении и может "утечь" в следующий, никак не связанный запрос другого пользователя,
который случайно получит то же самое физическое соединение из пула. `SET LOCAL` внутри
`$transaction` гарантированно сбрасывается при commit/rollback, до возврата соединения в пул.
**Это единственный корректный способ передавать tenant-контекст, и вне `withTenantContext`
устанавливать `app.current_teacher_id` запрещено.**

### 2.2 Слой 2 — PostgreSQL Row-Level Security (защита от бага в Слое 1)

```sql
ALTER TABLE "Lesson" ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "Lesson"
  USING (teacher_id = current_setting('app.current_teacher_id', true));
```

`current_setting(..., true)` со вторым аргументом `true` (`missing_ok`) возвращает `NULL`,
если переменная не установлена — сравнение `teacher_id = NULL` в SQL никогда не истинно,
значит политика **по умолчанию не пропускает ни одной строки**, если контекст не установлен
(fail-closed, не fail-open). Это стоит проверить отдельным тестом (§6).

### 2.3 Критично для Prisma: владелец таблицы обходит RLS по умолчанию

**Это не было учтено в первой версии документа и является главной находкой этого review.**
В PostgreSQL владелец таблицы (и роли с `BYPASSRLS`) **обходят RLS-политики даже когда RLS
включён**, если не применено `FORCE ROW LEVEL SECURITY`. Prisma по умолчанию выполняет
`prisma migrate deploy` под тем же пользователем БД, под которым и подключается runtime-код
приложения (`DATABASE_URL` в `.env` обычно один и тот же для миграций и рантайма) — то есть
пользователь, создавший таблицы (owner), и есть тот пользователь, под которым в проде выполняются
обычные запросы приложения. **Если это не разделить, RLS-политики из §2.2 не будут применяться
вообще, но ни один тест на уровне Prisma/приложения этого не заметит** — запросы просто
продолжат работать "как будто RLS нет" — потому что RLS "будто бы есть" (`rowsecurity = true`
в `pg_tables`), но не действует для владельца. Это ровно тот сценарий, где "мы включили RLS"
создаёт ложное чувство защищённости.

**Обязательное решение** (фиксируется как архитектурное требование, не опция):

1. Две отдельные роли Postgres:
   - `pomateshe_migrator` — владелец схемы, используется **только** для
     `prisma migrate deploy` (CI/CD-шаг, не рантайм-соединение).
   - `pomateshe_app` — рантайм-роль приложения, **не владелец** ни одной таблицы, без
     `BYPASSRLS`. Именно под этой ролью работает `DATABASE_URL` в рантайм-окружении Next.js
     и realtime-сервиса.
2. `pomateshe_app` получает `GRANT SELECT, INSERT, UPDATE, DELETE` на нужные таблицы явно
   (миграция это делает после создания таблиц) — без этого RLS-политики нечего будет
   разрешать (RLS ограничивает то, что и так разрешено GRANT'ами, не заменяет их).
3. Отдельная `admin`-роль БД (`pomateshe_admin_support`) для explicit support-режима (§5) —
   тоже без `BYPASSRLS`; вместо этого получает дополнительную permissive-политику
   `USING (true)`, применяемую только к этой роли, и используется через **отдельный,
   изолированный Prisma Client/connection pool**, который создаётся только в коде
   support-режима, недостижимом из обычных tenant-запросов (см. §5).
4. `FORCE ROW LEVEL SECURITY` дополнительно применяется на каждой tenant-таблице как
   defense-in-depth на случай, если в будущем кто-то по ошибке даст `pomateshe_app` права
   владельца — не заменяет разделение ролей из п.1-2, а страхует от его случайной отмены.

Каждая новая tenant-таблица должна в своей миграции: `ENABLE ROW LEVEL SECURITY`,
`FORCE ROW LEVEL SECURITY`, `CREATE POLICY`, `GRANT ... TO pomateshe_app` — все четыре пункта,
не только первый (чек-лист миграции обновлён в §7).

## 3. Идентификаторы, предсказуемость, кросс-тенантные сущности

### 3.1 Идентификаторы

Публичные ID (cuid2) непредсказуемы, но **не являются механизмом контроля доступа** — только
defense-in-depth. Публичная страница преподавателя использует `slug`, не внутренний `id`.

### 3.2 `TeacherStudentLink` — единственная таблица с двумя контекстами доступа

Это единственная таблица, к которой легитимно обращаются в двух разных контекстах:
преподаватель ("мои ученики") и ученик ("мои преподаватели"). Обе политики — permissive
(в Postgres несколько permissive-политик на одну команду объединяются через OR):

```sql
ALTER TABLE "TeacherStudentLink" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "TeacherStudentLink" FORCE ROW LEVEL SECURITY;

CREATE POLICY teacher_scope ON "TeacherStudentLink"
  USING (teacher_id = current_setting('app.current_teacher_id', true));

CREATE POLICY student_scope ON "TeacherStudentLink"
  USING (student_user_id = current_setting('app.current_student_user_id', true));
```

`withTenantContext` вызывается с ровно одним из двух ключей в зависимости от того, кто
выполняет запрос — учительский запрос ставит только `teacherId`, ученический — только
`studentUserId`. Никогда не ставятся оба одновременно для обычного запроса (это сузило бы,
а не расширило видимость, т.к. RLS combine — OR, а не AND, но смешение контекстов усложняет
аудит и не нужно ни в одном легитимном сценарии).

**Все остальные tenant-таблицы (`Lesson`, `Homework`, `MaterialFile`, `Group`, `Whiteboard`,
`GroupMember`) остаются под единой teacher-only RLS-политикой, как в §2.2.** Когда ученик
просматривает свои уроки у конкретного преподавателя, приложение сначала проверяет через
`TeacherStudentLink` (по `student_scope`), что связь активна, затем выполняет запрос к
`Lesson` уже с `teacherId` этого преподавателя в контексте (симметрично тому, как это делает
сам преподаватель) — **не вводится отдельная "ученическая" RLS-политика на каждую tenant-таблицу**,
чтобы не удваивать поверхность RLS-конфигурации ради единственного легитимного сценария
("список моих преподавателей"), который полностью покрывается `TeacherStudentLink`.

### 3.3 Прочие кросс-тенантные случаи

- `MaterialFile`, загруженный учеником — `teacherId` наследуется от `TeacherStudentLink.teacherId`
  в момент загрузки (в контексте конкретной связи, по которой открыто ДЗ), не выбирается клиентом.
- `Whiteboard` группового занятия доступна только участникам конкретного `Lesson` — токен
  комнаты выдаётся с явным списком разрешённых `userId`, не по факту "состоит в тенанте"
  (см. `docs/WHITEBOARD.md`).

## 4. Как tenant_id физически попадает в Postgres — сквозной пример

1. HTTP-запрос → middleware читает cookie сессии → находит `Session` в БД (эта таблица **не**
   tenant-scoped, у неё нет RLS — см. `docs/AUTH.md`) → получает `session.userId`, `session.role`.
2. Route handler/Server Action вызывает `getLessonsForTeacher(session, filters)` из
   data-access layer. Сама функция запрашивает `session.teacherId` — это поле **не берётся из
   клиента и не из JWT-claim, которым можно было бы манипулировать до подписи**, а
   подтягивается сервером из `TeacherProfile.userId = session.userId` при каждом вызове
   (не кэшируется в cookie) — так роль/привязка не может "устареть" в сторону избыточных прав.
3. `getLessonsForTeacher` вызывает `withTenantContext({ teacherId }, ...)`.
4. Внутри одной Postgres-транзакции: `SELECT set_config('app.current_teacher_id', $1, true)`,
   затем `SELECT * FROM "Lesson" WHERE teacher_id = $1` (сгенерировано Prisma).
5. Postgres применяет RLS-политику `tenant_isolation` к каждой строке `Lesson` независимо от
   того, что уже есть `WHERE teacher_id = $1` в запросе — избыточность намеренная (§2).
6. Транзакция коммитится → `app.current_teacher_id` сбрасывается → соединение возвращается в
   пул Prisma "чистым".

## 4.1 Найдено при реализации Phase 1: RLS-джойн через не-RLS таблицу возвращает `null`, не ошибку

**[Phase 1]** `StudentInvite` намеренно без RLS (см. комментарий модели в `schema.prisma` —
та же логика, что у `PasswordResetToken`: секретность обеспечивает сам токен, не тенантный
контекст). Но `prisma.studentInvite.findUnique({ include: { teacher: true } })`, вызванный
**без** установленного `app.current_teacher_id` (посетитель ссылки-приглашения ещё не
аутентифицирован ни как кто), возвращает `invite.teacher === null` — не ошибку, а именно
`null` — потому что джойн уходит в `teacher_profiles`, у которой RLS есть, и политика
"честно" отфильтровала недоступную строку. Поймано тестом (`src/server/__tests__/invites.test.ts`),
не при ручной проверке — в проде это было бы падением с "Cannot read properties of null" на
странице принятия приглашения.

**Практическое правило, actual для Phase 2**: чтение "публичного" (или просто уже известного
по ID) профиля через Prisma `include`/`select` вложенной relation, когда сам верхнеуровневый
объект запроса не требует контекста — не работает молча. Правильный паттерн, применённый в
`src/server/invites.ts` (`lookupInvite`): если teacherId уже известен из легитимного,
не завязанного на RLS источника (здесь — из самого приглашения; в Phase 2 для публичной
страницы преподавателя — из `slug`), **отдельным запросом** оборачивать чтение именно этого
профиля в `withTenantContext({ teacherId }, ...)` — RLS-политика при этом всё равно отдаёт
ровно одну, уже известную строку, не диапазон, так что это не ослабляет изоляцию. Публичная
страница преподавателя (`docs/ROADMAP.md` Phase 2) столкнётся с этим же паттерном и должна
использовать то же решение, а не отдельный "публичный" механизм в обход RLS.

## 4.2 Найдено при реализации Phase 1: "дан userId, найди teacherId" — паттерн §4.1 не решает

**[Phase 1]** У бага из §4.1 есть более серьёзный родственный случай: `getCurrentUser()`
(`src/lib/auth/current-user.ts`) после успешного логина должен ответить на вопрос "у этого
`userId` — какой `teacherId`?", чтобы решить, куда его пускать. Паттерн §4.1 ("если teacherId
уже известен из легитимного не-RLS источника — открой контекст на него") здесь **не работает**,
потому что teacherId — это ровно то, что нужно найти, а не то, что уже известно заранее.
Запрос `teacherProfile.findUnique({ where: { userId } })` без контекста возвращал 0 строк
всегда — что на практике означало: **ни один преподаватель не мог зайти в свой кабинет после
входа**, ни разу, независимо от пароля. Это не было пойдено ни одним из тестов §6 (все они
тестируют изоляцию МЕЖДУ известными тенантами, а не бутстрап "откуда взять первый teacherId
для этого пользователя") — обнаружено только реальным end-to-end прогоном через браузер.

Решение — не через RLS-политику, а денормализацией мимо неё: `User.teacherProfileId`
(`docs/DATABASE.md` §2), проставляется один раз при регистрации, читается напрямую с `User`
(у которой нет RLS) через JOIN в `validateSession`, без обращения к `teacher_profiles` вообще
для этого конкретного вопроса. Специально не стали заводить для этого случая третью
RLS-политику/третью session-переменную (по аналогии с `teacher_student_links`, §3.2) — это
усложнило бы модель RLS сразу в двух местах вместо одного, тогда как денормализация на `User`
решает именно этот один вопрос ("моё собственное teacherId") там, где он и задаётся, не
трогая RLS-модель `teacher_profiles` вообще.

**Практический вывод**: если где-то в будущем возникнет другой вопрос вида "дан X, не
связанный ещё ни с каким known-tenant-context, найди Y в RLS-защищённой таблице" — сначала
проверить, нельзя ли ответить на него с таблицы БЕЗ RLS (как здесь, через `User`), и только
если это в принципе невозможно — рассматривать новую RLS-политику. Добавлять политику по
умолчанию не надо: две из трёх найденных при реализации проблем с RLS в Phase 1 (эта и §4.1)
решились без единой новой политики.

## 4.3 Найдено при реализации Phase 2: публичная страница преподавателя нуждается в чтении БЕЗ контекста вообще

**[Phase 2]** До сих пор `withTenantContext` был единственным способом читать `teacher_profiles`
(§2.1) — но `/t/[slug]` (публичная страница, `docs/ROADMAP.md`) должна открываться анонимному
посетителю без какой-либо сессии, то есть без единого legitimate `teacherId`, который можно было
бы подставить в контекст, даже по аналогии с §4.1 ("если teacherId уже известен из
не-RLS-источника"). Здесь его просто не существует заранее — slug публичный и предназначен для
обнаружения кем угодно.

Решение — не денормализация (§4.2 здесь не подходит: нет исходного `User`, от которого можно
было бы оттолкнуться), а вторая, дополнительная RLS-политика на `teacher_profiles`:

```sql
CREATE POLICY public_read ON "teacher_profiles"
  FOR SELECT
  USING (true);
```

Существующая `tenant_isolation` (`FOR ALL`, `id = current_setting(...)`) никуда не делась —
Postgres складывает permissive-политики через OR для одной и той же команды, так что для
`SELECT` строка видна, если подходит хотя бы одна из двух: владелец через контекст, ИЛИ кто
угодно через `public_read`. `INSERT`/`UPDATE`/`DELETE` затронуты не были (у `public_read`
явно указано `FOR SELECT`) — запись по-прежнему требует контекста преподавателя.

**Важная оговорка**: RLS работает на уровне строк, не колонок — `public_read` открывает всю
строку целиком, а не только "публичные" поля. Разграничение на "что действительно показывать"
остаётся на уровне data-access слоя: `src/server/teacher-profile.ts`'s `getPublicTeacherProfile`
явно перечисляет `select` только тех колонок, что задуманы как публичные
(`bio`/`subjects`/`avatarStorageKey`/`avatarMimeType`/`contactInfo`/`defaultLessonPriceCents`/
`currency`/`displayName`/`slug`) — `zoomPersonalLink` и `publicPageSettings` туда сознательно
не включены и не должны быть добавлены без отдельного решения.

**Практический вывод, дополняющий §4.2**: не каждый "нет контекста" случай решается
денормализацией на `User` — когда легитимный доступ должен быть открыт вообще без
аутентификации (не "дан X, найди Y", а "это по определению публично"), вторая permissive-
политика для конкретной команды (здесь — только `SELECT`) является правильным, а не запасным
решением, при условии что она максимально узкая (одна команда, а не `FOR ALL`) и
data-access слой не полагается на неё как на замену выбора колонок.

## 4.4 Найдено при реализации Phase 2 (календарь): личные события не принадлежат ни одному тенанту

**[Phase 2]** Личные блоки календаря (`PersonalCalendarEvent` — "занят", "другая работа" и т.п.,
докс `docs/ROADMAP.md`) — не урок и не что-либо, принадлежащее преподавателю как тенанту:
их заводит себе и преподаватель, и ученик, и они не видны второй стороне вообще (полная
приватность — продуктовое решение владельца платформы). Ни один из двух существующих
контекстов не подходит:

- `app.current_teacher_id` — это `TeacherProfile.id`, а не `User.id` преподавателя. Личное
  событие преподавателя логически принадлежит его `User`, а не его "профилю преподавателя".
- `app.current_student_user_id` — по названию и смыслу относится только к роли ученика в
  контексте связи с преподавателем (`docs/MULTI_TENANCY.md §3.2`), не общий "я, независимо от
  роли".

Решение — третья, отдельная session-переменная `app.current_user_id`, которую
`withTenantContext` (`src/server/tenant-context.ts`) теперь умеет устанавливать наравне с
двумя существующими (`TenantContext.userId`, взаимоисключающе с `teacherId`/`studentUserId`).
RLS-политика на `personal_calendar_events` — `"ownerUserId" = current_setting('app.current_user_id', true)`,
без разделения на "преподавательскую" и "ученическую" версии: сущность одна и та же для обеих
ролей, значение `ownerUserId` — всегда `User.id`, независимо от того, что это за пользователь.

**Практический вывод**: не каждая новая сущность обязана вписываться в модель "тенант =
преподаватель" (§1) — если данные принадлежат ровно одному пользователю независимо от его
роли и не должны быть видны никому другому (даже связанной стороне), это отдельный, третий
паттерн доступа, а не повод либо искусственно привязывать сущность к `teacherId`, либо
disable RLS вовсе.

## 5. Доступ администратора (`admin`)

- По умолчанию `admin` **не видит** содержимое tenant-данных — видит только платформенные
  метрики и список преподавателей/статус аккаунтов (агрегаты через отдельные, явно
  неперсональные запросы — например, `COUNT(*)`, не `SELECT *`).
- Support-режим: запрос доступа с указанием причины → запись в `AuditLog` → временный доступ
  через `pomateshe_admin_support` роль БД (§2.3, п.3) и **отдельный Prisma Client instance**,
  инициализируемый только в изолированном модуле `src/server/admin-support/*`, недостижимом
  из обычного request-хендлинга. Обычный код приложения физически не имеет доступа к этому
  connection pool — это архитектурная, а не только процедурная защита от "случайно использовали
  admin-соединение для обычного запроса".
- Не реализуется в MVP до появления реального support-сценария (Правило 10 ТЗ), но модель
  данных (`AuditLog`, отдельная роль БД) закладывается заранее.

## 6. Тестирование изоляции (обязательная часть, не опционально)

См. развёрнутый список — `docs/TESTING.md` §2. Кратко, что проверяется:

1. HTTP-уровень: "преподаватель A не может прочитать/изменить/удалить ни одну сущность B".
2. RLS напрямую по SQL под ролью `pomateshe_app`, минуя приложение.
3. **Fail-closed без контекста**: запрос под `pomateshe_app` без `SET LOCAL` вообще (никто не
   вызвал `withTenantContext`) — должен вернуть 0 строк, не ошибку и не "все строки".
4. **Владение таблицами**: `pomateshe_app` не является владельцем ни одной tenant-таблицы;
   на каждой из них `rowsecurity = true` и `forcerowsecurity = true` в `pg_tables` —
   отдельный "schema policy" тест, гоняется в CI на каждую миграцию, а не вручную время от времени.
5. **Конкурентность**: два параллельных запроса от разных преподавателей, использующих один
   пул соединений, не видят контекст друг друга (проверяет корректность `SET LOCAL`/транзакций
   из §2.1, а не теоретическую гарантию).
6. **Webhook-сценарий**: входящий webhook от Google Calendar с валидным по формату, но чужим
   `channelId` не должен резолвиться в чужой `teacherId` (см. §7 таблицу рисков).

## 7. Риски, специфичные для этой модели

| Риск | Мера |
|---|---|
| `pomateshe_app` — владелец таблиц → RLS не действует незаметно для тестов приложения | Разделение ролей `migrator`/`app`/`admin_support` + `FORCE ROW LEVEL SECURITY` (§2.3), schema policy тест в CI (§6.4) |
| `SET` вместо `SET LOCAL` / установка контекста вне транзакции → утечка между запросами через пул соединений | Единственная точка входа `withTenantContext` (§2.1), конкурентный тест (§6.5) |
| Новый эндпоинт в обход data-access layer | Код-ревью чек-лист + RLS как страховка |
| Миграция создаёт новую tenant-таблицу без RLS/FORCE/GRANT/policy | Чек-лист миграции (§2.3, последний абзац) — все 4 пункта обязательны в одной миграции |
